How a Vector Works Inside

A growable array is three numbers and an address. Everything else — new, delete[], doubling, the leak — is bookkeeping to keep those three honest. This sheet explains every line of containers/vector.hpp and what to say when you are asked to defend it.

1. The whole idea, in one picture

A Vector is not a magic growable thing. It is a small object holding three pieces of state, one of which is the address of a block of memory somewhere else.

The invariant — the sentence that must be true after every single operation — is m_size <= m_capacity. Every bug in this file is a violation of that one line.

2. Pointers, from zero

This is the concept with no equivalent in any language you have written before, so it gets its own section.

An int holds a number. An int* — said aloud as pointer to int — holds the address of a number. It is a street address, not a house.

int  x = 42;      // x holds 42
int* p = &x;      // p holds "where x lives", e.g. 0x16f2ba3c8
                  // & means "address of"

*p = 99;          // * means "the thing at that address"
                  // x is now 99, and we never mentioned x

p[3] is the one that matters here. Indexing a pointer is not a special array feature — it is arithmetic. p[3] means "start at p, walk forward three ints, give me what is there." The compiler knows an int is four bytes, so it moves twelve.

Why this is dangerous Nothing checks that slot 3 is yours. p[3] compiles whether the buffer has four slots or one. C++ will happily read whatever bytes are at that address and hand them to you as an int. This is the entire reason AddressSanitizer exists, and section 8 shows it catching exactly this.

3. Why the heap at all

Local variables live on the stack. The compiler decides the layout of a stack frame while compiling — it emits one fixed number for "this function needs 48 bytes." That number is baked into the executable before your program has ever run.

So you cannot say "give me room for n ints" when n is not known until runtime. There is no compile-time size to bake in. That is the only reason the heap is in this file.

4. push_back, line by line

void push_back(int value)
{
    if (m_size == m_capacity)   // 1. no free slot?
        grow();                 //    buy more

    m_data[m_size] = value;     // 2. write into the first free slot
    ++m_size;                   // 3. one push, one increment
}

On the very first call both members are 0, so 0 == 0 fires and grow() allocates the first buffer. There is no separate "initialise" path; the empty vector is just the case where capacity has not been bought yet.

Step 2 uses m_size as the index because of the off-by-one that is not an off-by-one: if you hold three elements, they occupy slots 0, 1, 2 — so slot 3, which is m_size, is the first free one.

The bug worth knowing by name Writing m_data[m_size++] = value; and then ++m_size; increments twice. m_size++ already increments. The count then runs ahead of what is stored, and worse, it steps straight over m_capacity without ever being equal to it — so if (m_size == m_capacity) is never true again, grow() never runs, and every subsequent push writes past the end of a buffer that was never resized. Use =='s fragility as the lesson: >= would have survived it.

5. grow() — the only interesting function

A heap buffer cannot be resized in place. The memory directly after it may already belong to something else. So growing means making a second, larger buffer and moving in.

void grow()
{
    std::size_t new_capacity = (m_capacity == 0) ? 1 : m_capacity * 2;

    int *fresh = new int[new_capacity];         // 1. bigger buffer

    for (std::size_t i = 0; i < m_size; ++i)    // 2. copy the old values
        fresh[i] = m_data[i];                   //    m_size, not m_capacity

    delete[] m_data;                            // 3. release the old buffer
    m_data = fresh;                             // 4. adopt the new one
    m_capacity = new_capacity;
}

Two details worth defending out loud:

  • The loop runs to m_size, not m_capacity. Slots between the two have never been written; copying them would read uninitialised memory for no benefit.
  • m_capacity == 0 is special-cased because doubling zero is still zero. Without it the first grow() allocates a zero-length buffer and the next write is out of bounds.

6. Why doubling, and not +1

This is the design question you will be asked. The answer is a real reason, not a convention.

Copying is the expensive part of grow(). If capacity grew by one each time, every single push would reallocate and copy everything — n pushes would cost 1 + 2 + … + n copies, which is n²/2. Doubling makes the reallocations rare and geometric: the total copying across n pushes is n + n/2 + n/4 + … which sums to less than 2n.

So a push is not constant time — occasionally it is very expensive — but the average over any run of pushes is constant. The name for that is amortised constant time, and it is the phrase to use.

7. The leak you have deliberately left in

Nothing in the class ever calls delete[] on the final buffer. grow() frees each old buffer as it replaces it, so the intermediate ones are fine. But when v goes out of scope, its three members simply vanish — including m_data, which was the only record of where the last buffer lived.

The one-line fix, for when you get there:

~Vector() { delete[] m_data; }

A destructor runs automatically when the object goes out of scope. Tying the lifetime of a heap resource to the lifetime of a stack object is the idea called RAII, and it is the single most important pattern in the language. Buffer in containers/vec.hpp already does exactly this — compare the two files and the difference is that one line.

Do not stop there Adding a destructor alone makes things worse in one specific way: copying the vector then gives two objects holding the same pointer, and both will free it — a double free. That is why the destructor comes bundled with the copy constructor and copy assignment as a set, known as the Rule of Three. Knowing that this is coming is worth saying in review.

The leak, on an uninstrumented build

LeakSanitizer does not exist on Darwin, so the asan preset is silent. And -fsanitize=undefined in the dev preset makes Apple's leaks report zero as well — verified by holding the source constant and varying only that one flag. Leak checking therefore needs a third, plain build:

$ MallocStackLogging=1 leaks -atExit -- /tmp/leakcheck

48 bytes is the 8-slot buffer, four bytes per int, plus allocator overhead. Read the stack bottom-up and it is the whole call chain: main called push_back, which called grow, which called new[]. The leak is blamed on grow because that is the allocation site. Leak tools always report it that way — the delete[] you forgot has no location.

9. Defending it in review

If askedSay
Why doubling?Copying dominates. Doubling makes total copying across n pushes sum to under 2n, so pushes are amortised constant. Growing by a constant would make it quadratic.
Why is the copy loop bounded by m_size?Slots between size and capacity have never been written. Copying them would read uninitialised memory to no benefit.
Why delete[] after the copy, not before?Freeing first means the copy reads memory already returned to the allocator. It usually still prints correct output, which is what makes it dangerous.
Why no bounds check in operator[]?Matching std::vector, which does not check either; at() is the checked one. The unchecked read is caught by ASan instead, and I have the report.
Why does it leak?Deliberately, for now. No destructor, so the final buffer is never freed. I can show the 48-byte report. The fix is a destructor plus the rest of the Rule of Three, which is next.
Is it clean under the sanitizers?Clean under both presets — but that claim is weaker than it sounds, because neither preset detects leaks. That needs a third plain build and leaks.
What is still missing for P1?Templates (Vector<T> rather than int), copy and move semantics, iterators, and unordered_map.
