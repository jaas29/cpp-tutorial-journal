Glossary

The working vocabulary for this tutorial. Terms are added as lessons introduce them, and used consistently from then on — if a lesson says “translation unit”, it means exactly what it means here.

BUILD PIPELINE — from lesson 01

preprocessor
The first program in the build. Does purely textual work: pastes each #included file in wholesale, expands macros, deletes the #if branches that don't apply. It does not understand C++ — it has no concept of a function or a type. Stop the build here with clang++ -E.
translation unit
What the preprocessor hands to the compiler: one .cpp file with every header it included pasted in, applied recursively. This is the unit the compiler actually compiles, and it is compiled in complete isolation from every other translation unit in your project. The single most load-bearing term in this glossary. Most C++ file-layout rules are consequences of it.
compiler
Parses and type-checks one translation unit and emits assembly for it. Knows about that one file plus its headers, and nothing else in your project. clang++ -S.
declaration
States that a name exists and what its type is, with no body: int add(int x, int y);. A promise. Enough to satisfy the compiler.
definition
Provides the thing itself, body and all. Every name you actually use needs exactly one definition somewhere in the program — no more, no fewer. Enough to satisfy the linker. Every definition is also a declaration. The reverse is not true.
object file
A .o file: machine code for one translation unit, plus a symbol table recording which names it defines and which names it still needs. clang++ -c; inspect with nm.
symbol
A name as it appears in an object file's table. Functions and variables with external linkage get one.
name mangling
The compiler encoding a function's parameter types into its symbol name, so that overloads stay distinguishable at the object-file level. add(int, int) becomes __Z3addii; add(int, long) becomes __Z3addil. Decode with c++filt. Explains why a declaration/definition signature mismatch surfaces as a missing symbol rather than a type error.
linker
The last program in the build (ld). Sees every object file and library at once and matches each needed symbol to exactly one definition, then writes the executable. It works on names and addresses only — it does not know your types or see your source. Runs by default; there is no flag to “stop after” it.
undefined symbol
A name some object file uses that no object file defines. The linker's characteristic failure. Not a compiler error, because the compiler was shown a declaration and believed it.
duplicate symbol
The opposite failure: two object files both define the same name. Usually caused by a non-inline function or variable defined in a header that more than one .cpp included.
AddressSanitizer (ASan)
A compiler-inserted runtime memory checker: catches out-of-bounds access, use-after-free, double free, and some leaks, and reports the line that did it. Enabled at build time with -fsanitize=address; costs roughly 2–3× runtime, so it is a debugging build, never a benchmarking one. On this machine it must be built with Homebrew clang — see the toolchain sheet.
UndefinedBehaviorSanitizer (UBSan)
Sibling of ASan, for undefined behaviour rather than bad memory: signed overflow, invalid shifts, misaligned or null dereference. -fsanitize=undefined. Cheap; leave it on in debug builds.
