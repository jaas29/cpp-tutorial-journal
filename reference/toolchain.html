Build Pipeline & Error Triage

One clang++ command, four programs. Which one is talking to you, what it can and cannot know, and the flag that stops the pipeline there so you can look.

The four stages

StageStop after itProducesSeesTypical failure
Preprocess -E (add -P to drop line markers) a translation unit: one .cpp with every #include pasted in, recursively text only file not found, macro nonsense
Compile -S .s assembly exactly one translation unit syntax, types, overload resolution, template errors
Assemble -c .o object file + symbol table one .s file almost never fails
Link (the default: no flag) executable every .o and library at once — names only, no types Undefined symbols, duplicate symbol

The rule that explains the split: a declaration satisfies the compiler; only a definition satisfies the linker. The compiler believes promises. The linker collects debts.

Error triage table

Match the shape of the message, not the words. Compiler errors carry file:line:col and quote your source. Linker errors carry symbol names and an architecture, and often name no source line at all.

MessageStageWhat it actually means
fatal error: 'x.h' file not found preprocess Wrong path, wrong quotes, or missing -I directory.
error: use of undeclared identifier 'add' compile No declaration is visible in this translation unit. You probably forgot the #include.
error: no matching function for call to 'add' compile A declaration is visible but no overload accepts these arguments. Read the note: candidate lines — they tell you which ones it tried.
error: incomplete type / member access into incomplete type compile Only a forward declaration is visible; this use needs the full definition.
Undefined symbols … referenced from: _main in main.o link Something used it, nothing defined it. Causes, in order of likelihood: (1) the .cpp was never passed to the compiler; (2) declaration and definition signatures disagree, so the mangled names differ; (3) you declared a member function and never wrote its body; (4) a library is missing.
duplicate symbol '…' in: a.o, b.o link Two translation units both defined it. Usually a non-inline function or a non-inline variable defined in a header that two .cpp files included.
builds fine, wrong output or crash runtime Nothing above can help. This is what the sanitizers are for.
Fast test Not sure whether an error is compile or link? Build with -c. If the error survives, it is the compiler. If it disappears, it was the linker.

Inspecting object files

CommandShows
nm foo.oevery symbol. T = defined here (text/code), D = defined data, U = undefined (a hole), lowercase = local to this file.
nm -u foo.oundefined symbols only — the exact list the linker must satisfy.
nm foo.o | c++filtthe same, demangled: __Z3addii becomes add(int, int).
echo '__Z3addii' | c++filtdemangle one name you copied out of an error message.
otool -L ./progwhich shared libraries the executable needs at run time (macOS; ldd on Linux).

Name mangling. C++ encodes the parameter types into the symbol name so overloads stay distinct. __Z3addii is add with two ints; __Z3addil is add(int, long). Two names that differ by one letter are two unrelated functions to the linker — the reason a declaration/definition mismatch shows up as a missing symbol rather than a type error.

Flags worth memorising

FlagEffect
-std=c++20Pick the language version explicitly. Always set it; the default drifts between compilers.
-Wall -WextraTurn on the warnings that catch real bugs. Not on by default. Treat every one as an error to fix.
-WpedanticWarn on non-standard extensions — keeps code portable off your machine.
-gEmit debug info: real function names and line numbers in crashes and in the debugger.
-O0 / -O1 / -O2 / -O3Optimisation level. -O0 while debugging; -O2 for any timing measurement. Never benchmark a -O0 build.
-fsanitize=addressAddressSanitizer: catches out-of-bounds, use-after-free, double free, leaks. Pair with -g.
-fsanitize=undefinedUBSan: catches signed overflow, bad shifts, misaligned or null dereference.
-fno-omit-frame-pointerAdd alongside the sanitizers for readable stack traces.
-I<dir>Another directory to search for #include "..." headers.
-o <name>Name the output. Without it you get a.out.

Command lines to keep

# everyday build — Apple clang is fine here
clang++ -std=c++20 -Wall -Wextra -g -O0 main.cpp add.cpp -o prog

# UBSan — Apple clang is fine here too
clang++ -std=c++20 -Wall -Wextra -g -fsanitize=undefined main.cpp add.cpp -o prog-ub

# AddressSanitizer — MUST use Homebrew clang on this machine (see box below)
CXX=/opt/homebrew/opt/llvm/bin/clang++
$CXX -isysroot "$(xcrun --show-sdk-path)" \
     -std=c++20 -Wall -Wextra -g -fno-omit-frame-pointer \
     -fsanitize=address,undefined main.cpp add.cpp -o prog-san
./prog-san

# the build you take timings from
clang++ -std=c++20 -O2 -DNDEBUG main.cpp add.cpp -o prog-fast
This machine — read before Project 1

Apple clang's AddressSanitizer is broken on macOS 26.5. An -fsanitize=address binary built with /usr/bin/clang++ compiles and links fine, then hangs on startup, printing nothing. It is not your code and not a slow build. Verified by sampling the stuck process: ASan's shadow-memory setup calls a macOS 26 dyld routine that allocates memory, that allocation hits ASan's own intercepted malloc, and ASan re-enters its initialiser and spins forever on the lock it is already holding.

Use Homebrew LLVM for every ASan build (clang 22 ships a runtime without the bug). It needs -isysroot "$(xcrun --show-sdk-path)" or it cannot find the system headers. UBSan alone is unaffected — Apple clang is fine for that.

Careful The sanitizers instrument your code; a sanitizer build runs several times slower and is not the build you benchmark. Keep the two separate from day one. Sanitizer output is read top down: the first block is the bad access, then freed by, then previously allocated by. Within each stack, frame #0 is usually inside the ASan runtime — the first frame naming one of your files is the one you want.
ASan does not find leaks on macOS LeakSanitizer is not available on Darwin, so -fsanitize=address reports memory errors but stays completely silent about leaked allocations. Use Apple's leaks instead, on a normal (non-sanitizer) build, with the object out of scope before exit: 
MallocStackLogging=1 leaks -atExit -- ./build/dev/tests
It prints the leaked byte count and a stack naming the allocation site with file:line. Verified 2026-08-25 on this machine.

One-line glossary

  • Translation unit — one .cpp after preprocessing, with all its headers inlined. The unit the compiler actually compiles.
  • Declaration — states that a name exists and what its type is. No body.
  • Definition — provides the thing itself. Every declaration needs exactly one definition somewhere in the program.
  • Object file — machine code for one translation unit, plus a symbol table of what it defines and what it still needs.
  • Symbol — a name in an object file, mangled to encode its types.
  • Linker (ld) — matches undefined symbols to defined ones across all object files and libraries, and writes the executable.
