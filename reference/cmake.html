CMake & Sanitizer Builds

The commands, the file skeleton, and the two-compiler setup this machine requires. CMake generates build files; it never compiles anything itself.

Daily commands

cmake --build --preset devAfter every source edit. This is the one you type all day.

cmake --build --preset asan && ./build/asan/testsBefore every commit, and whenever something is mysterious.

CMakeLists.txt skeleton

cmake_minimum_required(VERSION 3.28)
project(containers LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)   # error rather than silently downgrade
set(CMAKE_CXX_EXTENSIONS OFF)         # -std=c++20, not -std=gnu++20
set(CMAKE_EXPORT_COMPILE_COMMANDS ON) # editor/clangd reads your real flags

add_library(containers INTERFACE)                       # header-only: compiles nothing
target_include_directories(containers INTERFACE ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_compile_options(containers INTERFACE -Wall -Wextra -Wpedantic -Werror)

add_executable(tests tests/main.cpp)
target_link_libraries(tests PRIVATE containers)         # inherits includes + flags

This machine's two compilers

Apple clang's AddressSanitizer hangs on startup under macOS 26. It builds and links fine, then produces nothing, forever. UBSan is unaffected. Full deadlock trace in learning record 0001.

Flags both presets share, and why:

  • -g — debug info. Without it sanitizer reports give addresses, not file:line.
  • -fno-omit-frame-pointer — keeps stack traces complete and correct.
  • CMAKE_BUILD_TYPE=Debug — -O0, so line numbers match your source.

Regenerate the sysroot path after any Xcode update:

xcrun --show-sdk-path
# /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk

Reading an ASan report

==58506==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000100
WRITE of size 4 at 0x602000000100 thread T0          <- 1. what, and read or write
    #0 0x000104c49534 in main main.cpp:6             <- 2. where it happened

0x602000000100 is located 0 bytes after 16-byte region [...]   <- 3. how far out
allocated by thread T0 here:                                    <- 4. where the memory came from
    #1 0x000104c49d1c in containers::Buffer::Buffer(unsigned long) vec.hpp:9

SUMMARY: AddressSanitizer: heap-buffer-overflow main.cpp:6 in main

Read frame #0 of the first trace first — that is your bug. The second trace is the allocation, which is usually in your library rather than at the fault. Ignore the shadow-byte dump unless you are debugging ASan itself.

Report saysMeans
heap-buffer-overflowIndexed past the end (or before the start) of a heap allocation.
heap-use-after-freeTouched memory after delete. The report names where it was freed.
attempting double-freeFreed twice. Usually a missing copy constructor.
stack-use-after-scopeKept a pointer or reference to a local that went out of scope.
LeakSanitizer: detected memory leaksAllocated and never freed. Not enabled by default on macOS.
runtime error: ... [UBSan]Not a memory error — signed overflow, bad shift, misaligned access, null deref.

Under UBSan, add -fno-sanitize-recover=all if you want the program to abort on the first violation instead of printing and continuing.

Common failures

SymptomCause
