Ownership and the Rule of Five

A class that holds a raw pointer to memory it allocated has taken on a job the compiler cannot do for it. This sheet is the five functions that job consists of, what each one must do, what happens if you leave it to the compiler, and the exact rule to cite when you are asked to defend the design.

1. The one question that decides everything

Does this class own a resource? Owning means: something was acquired that must later be released exactly once, and this object is the record of it. A heap buffer from new[], a file handle, a lock, a socket.

  • No — it holds only values, or non-owning references, or types that already manage themselves (std::vector, std::string, std::unique_ptr). Write none of the five. This is the Rule of Zero, and it is the right answer for almost every class you will write outside Project 1.
  • Yes — you are writing a container. All five are now your problem, because every one of the compiler’s versions is wrong for you.

2. The five, and what the compiler does if you say nothing

What declaring one does to the others

These five are entangled. Declaring any of them — and = delete counts as declaring — changes what the compiler generates for the rest. Nothing warns you.

You declareCompiler stops generatingHow you find out
Any constructor, including = deleteThe default constructorerror: no matching constructor on Vector v;
A destructorBoth move operationsYou do not. Every move becomes a copy.
A copy constructorBoth moves, and the default constructorHalf at compile time, half never
A move operationBoth copy operations (they are = deleted)error: call to deleted constructor

Hence Vector() = default; next to any = deleted copy constructor: it asks back for the zero-argument constructor that declaring the other one removed.

The trap in row two above Writing a destructor suppresses the generated move operations, and the copy operations are still generated but deprecated. So adding ~Vector() to a class silently changes what every move in your program does. Nothing warns you. This is the mechanical reason the Rule of Three became the Rule of Five.

3. What each one has to do

Destructor — release, once

~Vector() { delete[] m_data; }

delete[] on nullptr is defined and does nothing, so a default-constructed Vector needs no special case. Pair new[] with delete[]; crossing them with plain delete is undefined behaviour, not a warning.

Copy constructor — allocate your own, then copy the values

Vector(const Vector& other)
    : m_data(new int[other.m_capacity]),
      m_size(other.m_size),
      m_capacity(other.m_capacity)
{
    for (std::size_t i = 0; i < m_size; ++i)
        m_data[i] = other.m_data[i];
}

This is a deep copy: a second buffer, holding equal values. The default is a shallow copy: one buffer, two pointers. Copy m_size elements, not m_capacity — the slots past m_size were never written, and reading them is undefined behaviour even to copy them.

Copy assignment — guard, release, allocate, copy, return

Vector& operator=(const Vector& other) {
    if (this == &other) return *this;      // 1. self-assignment guard

    int* fresh = new int[other.m_capacity]; // 2. allocate BEFORE releasing
    for (std::size_t i = 0; i < other.m_size; ++i)
        fresh[i] = other.m_data[i];

    delete[] m_data;                        // 3. now release the old
    m_data = fresh;                         // 4. adopt
    m_size = other.m_size;
    m_capacity = other.m_capacity;
    return *this;                           // 5. always, for chaining
}

Two things it is easy to get wrong. Self-assignment: without the guard, v = v frees the buffer and then copies out of it. Order: allocating before releasing means that if new throws, the object is still intact rather than holding a dangling pointer.

Move constructor — steal, then blank the source

Vector(Vector&& other) noexcept
    : m_data(other.m_data), m_size(other.m_size), m_capacity(other.m_capacity)
{
    other.m_data = nullptr;     // essential
    other.m_size = 0;
    other.m_capacity = 0;
}

A move is a copy of the three members plus one obligation: leave the source in a state that is valid and safely destructible. Setting other.m_data = nullptr is what stops the source’s destructor from freeing the buffer you just took. Forget it and you have the same double free by a different route.

noexcept is not decoration. std::vector will refuse to use your move constructor when reallocating unless it is marked noexcept, and will copy instead.

Move assignment — guard, release, steal, blank

Vector& operator=(Vector&& other) noexcept {
    if (this == &other) return *this;
    delete[] m_data;                 // release what we currently hold
    m_data = other.m_data;           // steal
    m_size = other.m_size;
    m_capacity = other.m_capacity;
    other.m_data = nullptr;          // blank the source
    other.m_size = 0;
    other.m_capacity = 0;
    return *this;
}

4. Copy versus move, in one line

CopyMove
Buffers afterwardsTwoOne
CostProportional to sizeConstant — three assignments
Source afterwardsUnchangedValid but empty; do not read its values
Chosen forAn lvalue: a named objectAn rvalue: a temporary, or std::move(x)

std::move moves nothing. It is a cast that says “treat this named object as a temporary”, which is what lets overload resolution pick the move version. After std::move(a), a still exists and still gets destroyed — which is exactly why the move must leave it destructible.

5. The stopgap: = delete

Vector() = default;                        // required - see section 2
Vector(const Vector&) = delete;
Vector& operator=(const Vector&) = delete;

Makes the operation a compile error rather than a broken runtime behaviour. Use it when a type genuinely should not be copied (std::unique_ptr is defined this way), or as a deliberate placeholder while the real version is unwritten. Either way it satisfies the rule: “define or =delete them all.”

7. What to say in review

  • Core Guidelines C.21 — “If you define or =delete any copy, move, or destructor function, define or =delete them all.” The reason is the one in section 2: writing one changes what the compiler generates for the others.
  • C.20 — “If you can avoid defining default operations, do.” The Rule of Zero. The defence for writing all five in Project 1 is that a container is precisely the exception: you are implementing the ownership that everyone else gets to inherit.
  • C.66 — move operations should be noexcept.
