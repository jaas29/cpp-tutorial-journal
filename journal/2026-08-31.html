One line fixes the leak and creates a crash

Where I actually am

Took stock at the start of the week. Lessons 1–5 are done: four on the build system and one on the heap. p1-containers has two commits and a Vector of int that grows by doubling, with push_back, operator[], size and capacity — and a deliberate leak.

Against the Sep 2 deliverable, that is roughly the first third. Still missing: the destructor, copy semantics, move semantics, the template parameter, and iterators. Two days. The honest read is that this checkpoint will land partial, so the plan is to go in order of what a container is actually judged on — ownership first, generality last — and be able to defend the ordering rather than arrive with five half-finished things.

Worked through

Lesson 6 — The Destructor, and the Bug It Creates. A destructor is a member function the compiler calls at the closing brace, on every path out of the scope, including an exception unwinding through. ~Vector() { delete[] m_data; } and Lesson 5's leak is gone — verified on the third, unflagged build, since neither preset can see leaks:

Process 17726: 0 leaks for 0 total leaked bytes.

RAII is the name for the pattern, and it is a bad name: the half that matters is the release. Tie a resource's lifetime to an object's lifetime, and scope exit does the cleanup. Memory is only the example — files, locks and sockets are the same shape.

What broke, on purpose

Then containers::Vector b = a;. I never wrote a copy constructor, so the compiler wrote one, and its rule is to copy each member. m_data is a pointer, so it copied the address. Two objects, one buffer, and now two destructors that each free it.

Under the dev preset that is exit code 133 and nothing else. No message, no stack, not even the program's own last line of output, because the process is killed before stdout flushes. Under asan it is three stacks: freed here, freed again here, allocated in grow(). That is the clearest argument yet for carrying two toolchains, and it is recorded as learning record 0007.

The other half of it is quieter and arguably worse: I wrote to b[0] and a[0] changed. That is Java aliasing showing up in C++ by accident — a bug that exists before anything crashes.

Stopgap committed while the real fix is unwritten: Vector(const Vector&) = delete; and the same for copy assignment. A compile error naming a deleted function beats a silent abort.

New reference sheet

Ownership and the Rule of Five. All five special member functions, when the compiler generates each, what each has to do for a type that owns a buffer, and a symptom-to-cause triage table. The trap I did not know about: writing a destructor suppresses the generated move operations, so adding ~Vector() silently turned every move in the program back into a copy. That is the mechanical reason the Rule of Three became the Rule of Five, and it is the sheet I want next to me for the rest of this project.
