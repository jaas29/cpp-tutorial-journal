Asking why CMake exists, and getting an argument

Built

  • Project 1's build system, committed. Two presets, warnings as errors — the shape settled on 19 August, now real, in p1-containers.
  • newcpp, a small bash script at ~/.local/bin/newcpp that scaffolds a throwaway C++ project: CMakeLists, src/main.cpp, a .gitignore, a git repo, a configured build/, and a compile_commands.json symlink so the editor knows what is going on. Then it builds once, so I know the project works before I have written anything. -DSAN=ON adds sanitizers and supplies Homebrew clang's -isysroot itself.
  • Wrote it up as a runbook, including a Visual Studio to macOS translation table. Nearly all C++ video is Visual Studio on Windows, and that was the real thing slowing me down — not the C++, the button-pressing.
  • Wrote the toolchain and error-triage sheet.

Asked

I asked why we need CMake at all, since I had already compiled and linked by hand and could not see what it was doing that I could not type myself. The answer was to build the thing by hand first and then break it three ways:

  • Flag drift. The same flag list repeated per file, with nothing enforcing that they match.
  • No dependency graph — the one that actually matters. A shell script cannot know which .cpp included which header, so it has to rebuild everything or risk linking stale object files. We watched this live: editing a .cpp rebuilt one file, editing a header rebuilt all three, and then opened build/CMakeFiles/app.dir/compiler_depend.make to see where CMake had written that knowledge down.
  • Two configurations. My dev/asan split doubles every command if I am doing it by hand.

So: CMake is a generator, not a compiler and not a build system. Recorded as learning record 0004.

Watched

Loops and Control Flow quickly, then the two that mattered: POINTERS in C++ and REFERENCES in C++. A pointer is just an address, and the type on it is a promise about what is stored there — nothing more. I worked his new char[8] / memset / char** exercise through in mystl rather than just watching it.

References being pointers that cannot be null and cannot be repointed is what makes the int& return type on operator[] make sense, which I would otherwise have copied without understanding.

What broke

While preparing the next lesson, whose whole hook was going to be "write a Vector with no destructor and let AddressSanitizer show you the leak." I tested it first. It does not work.

A deliberately leaking Vector, built with -fsanitize=address,undefined and run with ASAN_OPTIONS=detect_leaks=1, ran to completion, printed the right answer, and exited 0 with no diagnostic. LeakSanitizer is not supported on Darwin at all, so the option is silently inert rather than failing loudly — which is worse.

What works instead is Apple's own leaks, on a plain Apple-clang build:

MallocStackLogging=1 leaks -atExit -- ./t2
Process 27743: 1 leak for 48 total leaked bytes.

and it prints the allocating stack, down to the line. Recorded as learning record 0005.
