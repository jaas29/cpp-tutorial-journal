Lesson 03 · Unscheduled · from your own broken build

The Linker Only Sees What You Listed

You split Log into its own file while following The Cherno, and the build stopped working. Nothing is wrong with your C++. The compiler read both files and was satisfied. What broke is one line of CMakeLists.txt — and understanding exactly why is worth more than the fix, because this error will find you again in every project this term.

Why this, nowYou hit it, so learn it properly

This is the first error you have seen that is not a compiler error. Telling those two apart on sight is a real skill, and it is on your mission list: "read a crash and know what it is before reaching for the debugger." Link errors are the easier cousin of that skill, and you have a live one to practise on.

Prerequisite This lesson assumes Lesson 1 — preprocessor, compiler, assembler, linker as four separate programs — and Lesson 2, where add_executable first appeared.

KnowledgeRead the error before anything else

Here is what your build actually printed. Read it as three separate facts, not one blob:

Undefined symbols for architecture arm64:
  "Log(char const*)", referenced from:
      ltmp1 in main.cpp.o
ld: symbol(s) not found for architecture arm64
  • ld: — the last line names the program that failed. Not clang++ compiling; ld, the linker. Everything compiled fine.
  • referenced from ... main.cpp.o — the file that wants the symbol. It is never the file with the problem.
  • "Log(char const*)" — the symbol nobody supplied. Note the full signature, not just the name. That detail matters later in this lesson.

A compiler error names a line in a .cpp file and a column. A linker error names a symbol and an .o file. That difference alone tells you which half of the pipeline to go looking in.

What your two files each promised

main.cpp contains a declaration:

src/main.cpp

void Log(const char* message);   // a promise, not a body

A declaration tells the compiler the shape of Log: it takes a const char*, it returns nothing. That is everything the compiler needs to check the call site and emit the right calling sequence. It does not need the body, and it does not go looking for one. It emits a call to a symbol and leaves a note: somebody fill this in later.

You can see the note. nm lists the symbols in an object file, and -u shows only the undefined ones — the holes:

$ nm -u build/CMakeFiles/mystl.dir/src/main.cpp.o
__Z3LogPKc
___cxa_atexit
___dso_handle

__Z3LogPKc is Log(char const*) after name mangling — the scheme C++ uses to encode a function's parameter types into its symbol name, so that overloads end up with distinct symbols. PKc is "pointer to const char". Pipe it through c++filt to read it back:

$ nm -u build/CMakeFiles/mystl.dir/src/main.cpp.o | c++filt
Log(char const*)

Meanwhile Log.cpp contains a definition — a declaration plus a body — and compiling it alone by hand produces exactly the symbol that hole is asking for. In nm's output, T means "defined here, in the text (code) section":

$ clang++ -std=c++20 -c src/Log.cpp -o /tmp/Log.o
$ nm /tmp/Log.o | grep ' T __Z3Log'
0000000000000000 T __Z3LogPKc

So the supply exists. The two halves simply never met.

The mechanismNothing crawls your src/ directory

Here is the assumption that broke you, and it is the natural one to make: I put Log.cpp in src/ next to main.cpp, so it is part of the project.

It is not. No part of the toolchain ever looks in a directory to find out what your program is made of. The compiler is handed one file at a time and knows nothing about any other. The linker is handed a list of .o files and knows nothing about any file not on that list. The only place that list is written down is add_executable.

Notice what #include did not do here. You did not include anything from Log.cpp, but even if you had written a header and included it, the outcome would be identical. #include is a paste operation performed by the preprocessor, and headers carry declarations. Declarations satisfy the compiler. Only object files satisfy the linker, and object files come from the source list.

PracticeDo this now

  1. Confirm the diagnosis before applying the fix. In mystl/, look at the hole:

    nm -u build/CMakeFiles/mystl.dir/src/main.cpp.o | c++filt

    You should see Log(char const*). Then confirm no Log.cpp.o exists anywhere:

    find build -name '*.o' | grep -i log

    Empty output. That is the whole bug, visible in two commands.

  2. Add the file to the target in CMakeLists.txt:

    CMakeLists.txt

    add_executable(mystl
    src/main.cpp
    src/Log.cpp
)

  3. Build. You do not need to reconfigure by hand — the generated Makefile has a rule that notices CMakeLists.txt changed and reruns CMake for you:

    cmake --build build

    Watch the output. It says Configuring done, then compiles Log.cpp.o, then links. It does not recompile main.cpp — that object file was already correct, and always was.

  4. Run it, and confirm the exit code while you are there:

    ./build/mystl
echo $?

    hello world, then 0.

The subtle versionThe same error, a different cause

Now the trap that catches people who have already learned the lesson above. Two files, both compiled, both linked — and still an undefined symbol:

// a.cpp
void Log(const char* m);          // declares Log(char const*)
int main(){ Log("hi"); }

// b.cpp
void Log(char* m){ /* ... */ }    // defines Log(char*)   ← not const
$ clang++ -std=c++20 a.cpp b.cpp -o demo
Undefined symbols for architecture arm64:
  "Log(char const*)", referenced from:
      _main in a-b202d1.o

Both files were compiled. Neither is missing. But because of name mangling, Log(char const*) and Log(char*) are different symbols — the linker matches on the mangled name, which encodes the parameter types, so a one-word difference in a signature makes the two halves invisible to each other. C++ overloading is exactly this mechanism working as intended; a typo'd signature is the same mechanism working against you.

The habit that prevents it Never hand-write a declaration in the file that calls the function, the way main.cpp does today. Put the declaration in a header, and #include that header from both main.cpp and Log.cpp. Then the definition and the call site read the same text, and a mismatch becomes a compiler error at the definition — caught earlier, and with a line number. That refactor is the next lesson.

RetrievalCheck yourself

  1. An error names a symbol and a .o file. Which stage?

    • Preprocessor expanding a header
    • Compiler checking your call site
    • Linker resolving an undefined symbol

  2. A declaration with no body anywhere. What does the compiler do?

    • Errors, because the body is missing
    • Succeeds, leaving an undefined symbol
    • Searches other files for the body

  3. A new .cpp sits in src/. What builds it?

    • Nothing, until CMakeLists lists it
    • CMake, which globs the source folder
    • The linker, when a symbol needs it

  4. Both files compiled, yet Log is undefined. Likely cause?

    • The header was included in order
    • The object files were built twice
    • The signatures differ, so symbols differ

Say out loud: why does adding a .cpp file to src/ change nothing until you edit CMakeLists.txt?

Because compilation is per-file and the file list is explicit. The compiler is invoked once per source file named in add_executable, and each invocation sees only that one file. A .cpp not on the list is never handed to the compiler, so no object file is produced, so its symbols never enter the set the linker searches. Location on disk is irrelevant — nothing in the toolchain scans directories to discover sources.
