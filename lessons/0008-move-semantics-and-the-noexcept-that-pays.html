Move Semantics, and the noexcept That Pays

Lesson 7 made copying correct. This lesson is about the copies you should not be making at all. There is a bug in your Vector right now that produces no crash, no leak, and no sanitizer report — it just quietly allocates and copies a buffer every time you hand a Vector somewhere. You wrote it in Lesson 6, in one line, and nothing has warned you about it since.

Knowledge 1The bug your destructor introduced

Here is the measurement, run on your machine against the commit you pushed this morning. The probe counts every new int[] by replacing operator new[] globally, so the numbers are allocations of your buffer and nothing else:

after building a:            4 allocations   (1 -> 2 -> 4 -> 8, doubling)
Vector b = std::move(a):     1 allocation
c = std::move(b):            1 allocation

You asked for a move and paid for a copy. std::move is right there in the source and it allocated a buffer anyway. The reason is a rule from the ownership sheet that has been true since Lesson 6 and has never once produced a diagnostic:

Declaring a destructor stops the compiler generating both move operations. Not “makes them wrong” — makes them not exist. And when a move operation does not exist, the call does not fail. Overload resolution falls back to the next thing that can accept an rvalue, which is const Vector&, which is your copy constructor. The program stays correct and gets slower, forever, silently.

This is the single most important entry in the Rule of Five table, because it is the only one with no error message attached. A missing destructor leaks and leaks tells you. A missing copy constructor double-frees and ASan tells you. A missing move constructor tells you nothing at all.

Knowledge 2What a move actually is

A copy answers: make me a second one, and leave the original alone. A move answers a different question: the original is about to die — give me its buffer.

That second question is answerable in four pointer assignments and no allocation. The whole operation is: take the source's pointer, then blank the source so its destructor has nothing left to free.

std::move does not move anything

It is a cast, and nothing else. std::move(a) produces an rvalue reference to a — written Vector&& — which is a way of saying “you may treat this object as expendable.” No code runs. All it does is change which overload the compiler picks. If no Vector&& overload exists, the cast is pointless and the copy runs, which is exactly the 1 allocation you measured above. The name is one of the worst in the standard library; read it as std::treat_as_expendable.

Build 1The move constructor

In include/containers/vector.hpp, below your copy assignment operator and still in the public: block — the five belong in one run:

include/containers/vector.hpp

        // Move constructor: take other's buffer instead of duplicating it.
        // Called by `Vector b = std::move(a);` and when a function returns a
        // temporary. No allocation, no copy loop - just four pointer-sized writes.
        Vector(Vector &&other) noexcept
            : m_data(other.m_data),
              m_size(other.m_size),
              m_capacity(other.m_capacity)
        {
            // The half people forget. Without this, other still holds the address,
            // and its destructor frees the buffer b is now using. Same double free
            // as Lesson 6, arrived at from the opposite direction.
            other.m_data = nullptr;
            other.m_size = 0;
            other.m_capacity = 0;
        }

No const on the parameter, and that is the point: you are about to modify other. A move that leaves the source untouched is a copy.

Note what makes the blanking safe rather than merely tidy. delete[] nullptr is defined by the standard to do nothing, so the moved-from object's destructor is already correct with no special case. That is the same guarantee your grow() has relied on since Lesson 5 for the first allocation.

Knowledge 3What a moved-from object is allowed to be

After Vector b = std::move(a);, what is a? The standard's answer for its own types is valid but unspecified: you may destroy it, and you may assign a new value to it, but you may not assume what it contains.

Yours is stronger than that, and deliberately so. Blanking to nullptr/0 leaves a moved-from Vector indistinguishable from a default-constructed one, which means it is not just destructible but genuinely reusable. Measured:

moved-from a: size 0 cap 0
after push_back: a[0] = 7 size 1        # a works again, from empty
after self-move b: size 5               # b survived b = std::move(b)

Both lines under ASan and UBSan with no report, and 0 leaks for 0 total leaked bytes on the third build. The empty state costs you nothing to provide and removes an entire category of question from your code review, so provide it.

Build 2Move assignment

Same relationship to the move constructor as copy assignment had to the copy constructor: *this is already alive and already owns a buffer, so there is a release to do first.

include/containers/vector.hpp

        Vector &operator=(Vector &&other) noexcept
        {
            if (this == &other) return *this;   // self-move: without this, we free
                                                 // our own buffer and then adopt it
            delete[] m_data;                     // release what we hold
            m_data = other.m_data;               // adopt theirs
            m_size = other.m_size;
            m_capacity = other.m_capacity;
            other.m_data = nullptr;              // and blank them
            other.m_size = 0;
            other.m_capacity = 0;
            return *this;
        }

Read the guard here against record 0008, because the conclusion flips. In copy assignment you measured that the guard is an optimization: allocate-before-release makes self-assignment correct on its own. In move assignment there is no allocation to reorder. Delete comes first because it must, so b = std::move(b) without the guard frees the buffer and then adopts the pointer to it — a genuine use-after-free. Here the guard is load-bearing. Same two words, opposite answers, and you can now say why for each.

Now rerun the probe:

Vector b = std::move(a):     0 allocation(s)
c = std::move(b):            0 allocation(s)

Knowledge 4What noexcept buys — measured

Both signatures carry noexcept. It is not decoration, and the reason is worth having straight because it is a favourite review question.

std::vector reallocating has a problem: it must relocate your elements to a bigger buffer, and if relocation throws halfway through, the old buffer is already partly gutted and there is nothing to roll back to. Copying is safe here — the original is untouched until every copy has succeeded. So std::vector will only use your move constructor if you have promised it cannot throw. If you have not, it copies, and never mentions it.

Eight Vectors of three elements pushed into a std::vector<Vector>, counting buffer allocations, identical source but for the keyword:

Move opsis_nothrow_move_constructibleAllocationsWhat the extra ones are
marked noexcepttrue243 per Vector, building them. Nothing else.
not markedfalse31Same 24, plus 7 buffers copied during regrowth

The extra seven are exactly the 1 + 2 + 4 elements that std::vector relocates as it doubles from capacity 1 to 8. Both programs print shelf[7][2] = 2; both are correct; one does 30% more allocation because of a missing keyword. That is the shape of every performance bug you will meet in this project — not a wrong answer, a right answer bought too dearly.

The rule to carry: a move operation that cannot throw must say so. Yours cannot throw — it copies pointers and integers and calls delete[], and none of those allocate. Say so.
