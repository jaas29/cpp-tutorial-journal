Lesson 09 · Weeks 3–4 · Project 1

Vector<T>, and the Bug int Was Hiding

The mechanical part of this lesson takes ten minutes: write template <typename T> and replace int with T. The reason it is worth a lesson is what happens next. Templating is a test. The moment T is a type that owns memory, your container starts reporting on decisions that were free when T was int — and one of them turns out to be wrong.

Knowledge 1What a template actually is

A template is not a type. It is a recipe the compiler uses to write a type, once per T you actually use. Write Vector<int> and Vector<Vector<int>> in one program and the compiler generates two complete, unrelated classes — that generation step is called instantiation.

Two consequences you will meet immediately:

  • Errors arrive late, and from inside your header. Nothing in Vector<T> is checked until some T is supplied. A mistake in grow() is reported at the line in your header that failed, with a “in instantiation of member function ... requested here” note pointing back at the caller. Read those notes bottom-up: the last one is the line you wrote.
  • Templates stay in the header. The compiler needs the full body at every call site to instantiate it. Your library is already header-only (record 0002), so this changes nothing for you — but it is why std::vector ships as a header, and worth being able to say why.

Build 1The mechanical part

Four edits in include/containers/vector.hpp:

    template <typename T>          // 1. above `class Vector`
    class Vector
    {
        T *m_data = nullptr;        // 2. the member type

        void push_back(const T &value)   // 3. see below
        T &operator[](std::size_t index)

        T *fresh = new T[new_capacity];  // 4. every `new int[` and `int *fresh`

Leave m_size and m_capacity as std::size_t. They count slots, not elements — they have nothing to do with T.

Inside the class body you may keep writing plain Vector rather than Vector<T>. That is the injected class name: within its own definition, a class template refers to its current instantiation by its bare name. So your five special members need no edits at all.

Why push_back changes to const T&

void push_back(int value) took its argument by value, which was exactly right for an int — copying four bytes is cheaper than the indirection of a reference. But T might be a Vector<int>, or a type holding a megabyte. Taking it by value would deep-copy the argument into the parameter and then copy it again into the buffer: two copies where the caller asked for one. const T& makes it one copy for every T, at the cost of an indirection for the small ones. That is the trade std::vector makes too.

Knowledge 2Record 0008's open question, answered

You left a question open on purpose when you wrote record 0008: does the allocate-copy-release conclusion still hold once T has a non-trivial copy assignment of its own? Self-assigning the buffer and self-assigning the elements one by one are different questions.

It is now testable, so it was tested — Vector<Vector<int>>, self-assigned through a reference, then deep-copied and mutated one level down, under ASan and UBSan with -Werror:

Vector<Vector<int>>  outer[2][3] = 23
after self-assign  outer[2][3] = 23  size 3      # unchanged, correct
outer[2][3] = 23   copy[2][3] = 999              # copies are independent
exit 0, no sanitizer report, 0 leaks

The answer is yes, and the reason is the ordering, again. With allocate-first, fresh is a brand-new array when the copy loop runs, and each fresh[i] = other.m_data[i] invokes T's copy assignment on a fresh destination and an untouched source. No element is ever its own source. The guarantee composes: because the buffer-level ordering is correct, the element-level operation never sees an aliasing case at all.

Go and close that section of record 0008.

Knowledge 3The bug int was hiding

Now the part worth the lesson. Look again at grow(), unchanged since Lesson 5:

            T *fresh = new T[new_capacity];
            for (std::size_t i = 0; i < m_size; ++i)
                fresh[i] = m_data[i];        // <-- this line
            delete[] m_data;

That line copies every element into the new buffer. Then the very next line destroys the originals. You are deep-copying data whose only remaining future is to be deleted — which is the precise situation Lesson 8 defined a move for.

While T was int, this cost exactly nothing, and no measurement could have told you otherwise: moving an int is copying an int. The decision was invisible because the test data could not see it.

Measured on this machinegrow() copiesgrow() moves
5 push_backs into Vector<int>4 allocations4 allocations
8 rows into Vector<Vector<int>>43 allocations36 allocations

Seven allocations saved, and they are the same seven as last lesson: 1 + 2 + 4, the elements relocated as the outer buffer doubles from capacity 1 to 8. In Lesson 8 you watched std::vector pay that tax because your move was not noexcept. Here your own container is paying it because grow() never asks for a move at all.

The top row is the lesson. Identical numbers, because at T = int the two versions compile to the same thing. A test that only ever instantiates Vector<int> cannot distinguish a correct grow() from a wasteful one. The template did not introduce this bug; it made it observable.

Build 2One word

include/containers/vector.hpp — in grow()

            for (std::size_t i = 0; i < m_size; ++i)  // 2. MOVE the old values
                fresh[i] = std::move(m_data[i]);

Add #include <utility> at the top of the header while you are there.

This is safe for exactly the reason Lesson 8 established: m_data[i] is about to be destroyed by the delete[] two lines down, so leaving it blanked costs nothing. And it is correct for every T, including ones with no move operations at all — std::move is only a cast, so a T without a move assignment simply resolves to its copy assignment, exactly as before. You cannot lose by asking.

Knowledge 4What new T[] costs you

One honest limitation, so you are not surprised by it in review. new T[n] default-constructs all n elements. Two consequences:

  • Your Vector cannot hold a type that has no default constructor. Measured: 
    struct Point { int x, y; Point(int a, int b) : x(a), y(b) {} };
containers::Vector<Point> v;

error: no matching constructor for initialization of 'Point[]'
   128 |             T *fresh = new T[new_capacity];
  • Reserving capacity constructs objects in slots nobody has stored anything in yet — work done for values that will be overwritten.

std::vector has neither problem, because it does not use new T[]. It allocates raw bytes and constructs each element in place, only when you push it. That is a real and worthwhile next step, and it is deliberately not this lesson: it needs placement new, explicit destructor calls, and an allocator, and it would swamp the one idea here. Note it as known, and be able to say what the fix is called.

SkillRetrieval

  1. What does the compiler do with a class template?

    • Compiles one shared class
    • Generates one class per type
    • Defers all checks to runtime
    • Erases the type parameter

  2. Why must template definitions live in the header?

    • Headers compile much faster
    • The linker demands one copy
    • To keep the build simpler
    • Each use needs the body

  3. Which bug did T = int make invisible?

    • grow copied instead of moving
    • push_back took its argument twice
    • The guard was in backwards
    • Capacity doubled one step late

  4. What if T has no move assignment at all?

    • The header fails to compile
    • The elements are left blanked
    • It falls back to copying
    • The compiler generates one

  5. What does new T[n] require of T?

    • A publicly declared destructor
    • A default constructor exists
    • A noexcept move assignment
    • A copy constructor exists

Out loud: your Vector<int> tests passed identically before and after fixing grow(). Say why, and say what that tells you about the test suite rather than about the code.

Because moving an int is copying an int — both versions compile to the same instructions for that instantiation. It says the test suite was never capable of distinguishing the two: a container is only as tested as its most demanding element type, and int is the least demanding one there is.
