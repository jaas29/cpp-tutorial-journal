CMake Is Not a Build System

You can build Project 1 by hand. Four clang++ commands, no CMakeLists.txt, done. So the honest question is not “how do I use CMake” but “what breaks when I don’t.” Three things break. This lesson breaks them on purpose, then shows what CMake actually is — which is not what most people assume.

Set-upThe program we are building by hand

Three sources and one header — the same shape mystl already has:

include/log.hpp     declares  void Log(const char*);
src/log.cpp         defines   Log
src/vecutil.cpp     defines   Report, calls Log
src/main.cpp        calls     Log and Report

From Lesson 1: the compiler handles exactly one translation unit at a time. So building this by hand is three compiles and one link, and there is nothing clever about it.

clang++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -g -Iinclude -c src/main.cpp    -o obj/main.o
clang++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -g -Iinclude -c src/log.cpp     -o obj/log.o
clang++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -g -Iinclude -c src/vecutil.cpp -o obj/vecutil.o
clang++ -g obj/main.o obj/log.o obj/vecutil.o -o app
$ ./app
hello
vecutil reporting

That works. Every command above was run on your machine to produce that output. Keep it in mind as the baseline: CMake does not do anything you could not type yourself. It types these for you, and it decides which of them to type.

Break 1The flag list has to be identical everywhere

Look at what repeats: -std=c++20 -Wall -Wextra -Wpedantic -Werror -g -Iinclude, three times, character for character. Nothing enforces that. Drop -Iinclude from one line and that file alone fails to find the header. Drop -Werror from one line and that file alone silently accepts a warning — and it will be the file you did not check.

Worse is the case where the flags disagree in a way that still compiles. Two files built with different values of a macro, or against different standard versions, link happily and then misbehave at runtime. This is the same failure family as the signature mismatch in Lesson 3: the toolchain will not stop you, because from its point of view you meant it.

CMake’s answer is that flags belong to a target, not to a command line. You say it once:

CMakeLists.txt

add_executable(app src/main.cpp src/log.cpp src/vecutil.cpp)
target_include_directories(app PRIVATE include)
target_compile_options(app PRIVATE -Wall -Wextra -Wpedantic -Werror -g)

Every source in that target now gets exactly the same treatment, by construction. The PRIVATE/PUBLIC/INTERFACE keywords are how that inheritance is controlled — the table in the CMake reference sheet is the one to keep open.

Break 2You do not know what needs rebuilding

This is the real one, and it is the reason build systems exist at all.

You edited one file. Which of those four commands do you need to re-run? Re-running all of them is always correct and always wasteful — and P1’s templates plus P2’s ray tracer will make “wasteful” mean minutes, every save. Re-running only the obvious one is fast and sometimes wrong: if you changed log.hpp, then main.cpp and vecutil.cpp both need recompiling too, because both included it. You linked stale object files and you will not be told.

Getting this right means knowing which .cpp pulls in which header — transitively, through headers that include headers. A shell script cannot know that. CMake asks the compiler, records the answer, and uses it. Here is that happening, real output from your machine:

$ printf '\n// tweak\n' >> src/vecutil.cpp
$ cmake --build build
[ 25%] Building CXX object CMakeFiles/app.dir/src/vecutil.cpp.o
[ 50%] Linking CXX executable app
[100%] Built target app

One file changed, one file recompiled. Now the header:

$ printf '\n' >> include/log.hpp
$ cmake --build build
[ 25%] Building CXX object CMakeFiles/app.dir/src/main.cpp.o
[ 50%] Building CXX object CMakeFiles/app.dir/src/log.cpp.o
[ 75%] Building CXX object CMakeFiles/app.dir/src/vecutil.cpp.o
[100%] Linking CXX executable app
[100%] Built target app

All three, because all three include it. Nobody told CMake that. It is written down in a file it generated, which you can read:

build/CMakeFiles/app.dir/compiler_depend.make

CMakeFiles/app.dir/src/vecutil.cpp.o: .../src/vecutil.cpp \
  .../include/log.hpp

Read that as a sentence: this object file is out of date if either of these two files is newer than it. That is the whole idea. A build system is a dependency graph plus the rule “rebuild anything older than what it depends on.”

Why this bites you specifically P1 is header-only. Your vector.hpp is the code, so every test file depends on it and every edit rebuilds all of them. Header dependency tracking is not a detail in this project — it is the main event.

Break 3You need two builds, not one

From Lesson 2: your asan build uses a different compiler, extra sanitizer flags, and an -isysroot. By hand, that is a second complete set of the four commands, kept in sync with the first forever, writing to different object files so the two toolchains’ output never mixes. Two build directories and one source tree is a thing CMake is built to do and a thing hand-typing is bad at.

KnowledgeSo what is CMake

Here is the part that is usually skipped, and it explains the two-command workflow that otherwise looks arbitrary.

CMake does not build your program. CMake writes a program that builds your program. It is a build system generator. On this machine it reads your CMakeLists.txt and writes Makefiles into build/; make then runs those. That is why there are two steps and why they have different triggers.

You can read what it generated. This file is CMake’s translation of your three lines of flags into the literal command line it will use:

build/CMakeFiles/app.dir/flags.make

CXX_INCLUDES = -I/.../whycmake/include
CXX_FLAGS = -std=gnu++20 -arch arm64 -Wall -Wextra -Wpedantic -Werror -g

Compare that to the hand-typed command at the top of this lesson. Same flags, one source of truth. Note -std=gnu++20, not -std=c++20 — CMake enables GNU extensions by default. That is precisely why your mystl/CMakeLists.txt carries set(CMAKE_CXX_EXTENSIONS OFF): it turns that into plain -std=c++20, so the compiler rejects non-standard code instead of quietly accepting it.

The one-sentence version CMake exists so that “what my program is made of” is written down once, in a file, in a form that is portable across compilers and operating systems — instead of living in your shell history.

SkillRetrieval

  1. What runs the clang++ commands that produce your object files?

    • CMake, during the configure step
    • CMake, during the compile step
    • Make, using files CMake wrote
    • Make, using files you wrote

  2. You edit log.hpp, included by all three sources. What gets recompiled?

    • The header only, then relink
    • Nothing; headers are not compiled
    • Only the source you last edited
    • All three sources, then relink

  3. Which change requires re-running the configure step?

    • Editing the body of a function
    • Adding a file to a target
    • Renaming a local variable
    • Fixing a compiler warning

  4. A shell script of four clang++ lines fails hardest at which job?

    • Rebuilding only the stale files
    • Applying the same flags twice
    • Finding headers in include/
    • Passing sanitizer flags to clang

Out loud, in one sentence: what is the difference between cmake -B build and cmake --build build?

The first reads CMakeLists.txt and generates a build system into build/. The second runs that build system. Configure after editing CMakeLists.txt; build after editing source.

Do this nowTen minutes in your own repo

  1. In ~/projects/cpp-tutorial/mystl, run cmake --build build twice in a row. The second prints Built target mystl and nothing else — that is the dependency graph telling you there is no work to do.
  2. Open build/CMakeFiles/mystl.dir/flags.make and find your own -Wall -Wextra -Wpedantic in it. Confirm the -std= says c++20, not gnu++20 — that is your CMAKE_CXX_EXTENSIONS OFF doing its job.
  3. Touch a header in include/, rebuild, and watch which files recompile. Predict the list before you press enter.
  4. Run cmake --build build -v once. It prints the full clang++ command lines. They should look like the hand-typed ones at the top of this lesson.
