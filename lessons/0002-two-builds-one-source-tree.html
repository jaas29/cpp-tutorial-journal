Two Builds, One Source Tree

In Lesson 1 you typed the pipeline by hand. Today you hand that typing to CMake — and get something you could not get by hand: the same source compiled two different ways, by two different compilers, at the same time. By the end you have the repository you will build Project 1 in.

Why this, nowYou need two compilers, not one

Project 1's success criterion is "runs clean under AddressSanitizer and UBSan." On this machine that criterion is not reachable with one compiler. Apple clang's AddressSanitizer hangs on startup under macOS 26 — it compiles, it links, and then it sits there forever producing nothing. UBSan is fine; ASan is not (learning record 0001 has the deadlock trace).

So you need Homebrew's clang for sanitizer runs and Apple clang for everything else. Doing that by hand means two different long command lines that you must not mix up, and two sets of .o files that must never land in the same directory. That is exactly the kind of bookkeeping you should never do with your fingers.

Mission link This is week-1 infrastructure for the container library. Every lesson from here on assumes cmake --build --preset asan works, because from Project 1 onward the sanitizer run is the test.

KnowledgeCMake does not compile anything

The single most useful thing to know: CMake is not a compiler and not a build system. It is a generator. It reads your CMakeLists.txt and writes out the input files for a real build tool, which then runs the four programs from Lesson 1.

That is why there are always two steps, never one:

StepCommandWhat happensHow often
Configure cmake --preset dev Finds the compiler, tests what it supports, writes build files into a build directory. Once — and again when you edit CMakeLists.txt.
Build cmake --build --preset dev Runs the generated build tool, which runs clang++ -c and then links. Every time you change code.

Out-of-source builds

Every generated file — object files, executables, CMake's own cache — goes into a build/ directory that is not under version control. Nothing generated ever sits next to your source. Two consequences worth internalising:

  • Deleting build/ can never lose work. When a build goes strange, deleting it is the correct first move, not a desperate one.
  • Two build directories means two complete, independent sets of object files. The Apple-clang .o files and the Homebrew-clang .o files can never accidentally be linked together.

Targets, and why every command starts with target_

Modern CMake is built around targets: named things you build (a library, an executable). You never set flags globally. You attach properties to a target, and targets that link against it inherit those properties automatically. That inheritance is the whole design (official CMake tutorial).

Three keywords control how far a property spreads:

KeywordApplies to the target itselfSpreads to whoever links it
PRIVATEyesno
PUBLICyesyes
INTERFACEnoyes

Your container library will be templates, which means it lives entirely in headers and has no .cpp of its own to compile. CMake has a name for that shape: an INTERFACE library. It compiles nothing. It is a named bundle of include paths and flags that gets handed to anything linking it.

SkillBuild the Project 1 repository

Do this in ~/Projects/, per your workspace convention — never in this teaching workspace.

  1. Make the tree.

    mkdir -p ~/Projects/p1-containers/{include/containers,tests}
cd ~/Projects/p1-containers
git init

  2. Write CMakeLists.txt. Six meaningful lines of setup, then two targets.

    CMakeLists.txt

    cmake_minimum_required(VERSION 3.28)
project(containers LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)   # error out rather than silently downgrade
set(CMAKE_CXX_EXTENSIONS OFF)         # -std=c++20, not -std=gnu++20
set(CMAKE_EXPORT_COMPILE_COMMANDS ON) # so your editor knows your flags

add_library(containers INTERFACE)
target_include_directories(containers INTERFACE ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_compile_options(containers INTERFACE -Wall -Wextra -Wpedantic -Werror)

add_executable(tests tests/main.cpp)
target_link_libraries(tests PRIVATE containers)

    The last line is the one doing real work. tests links containers, so it inherits both the include path and the warning flags. You never repeat them.

  3. Write the two source files. A deliberately tiny stand-in for the real vector, so today's lesson stays about the build.

    include/containers/vec.hpp

    #pragma once
#include <cstddef>

namespace containers {

class Buffer {
public:
    explicit Buffer(std::size_t n) : data_(new int[n]), size_(n) {}
    ~Buffer() { delete[] data_; }

    int& operator[](std::size_t i) { return data_[i]; }
    std::size_t size() const { return size_; }

private:
    int* data_;
    std::size_t size_;
};

}  // namespace containers

    tests/main.cpp

    #include <containers/vec.hpp>
#include <iostream>

int main() {
    containers::Buffer b(4);
    for (std::size_t i = 0; i < b.size(); ++i) b[i] = static_cast<int>(i * i);
    std::cout << b[3] << '\n';
}

    Note #include <containers/vec.hpp> with angle brackets, not quotes. It works because target_include_directories put include/ on the search path — the same mechanism <iostream> uses. Your library is now found the way a real library is.

  4. Write CMakePresets.json. This is the file that saves you from memorising two compiler paths and two flag sets.

    CMakePresets.json

    {
  "version": 6,
  "configurePresets": [
    {
      "name": "dev",
      "displayName": "Everyday build (Apple clang, UBSan)",
      "binaryDir": "${sourceDir}/build/dev",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_COMPILER": "/usr/bin/clang++",
        "CMAKE_CXX_FLAGS": "-g -fno-omit-frame-pointer -fsanitize=undefined"
      }
    },
    {
      "name": "asan",
      "displayName": "Sanitizer build (Homebrew clang, ASan + UBSan)",
      "binaryDir": "${sourceDir}/build/asan",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_COMPILER": "/opt/homebrew/opt/llvm/bin/clang++",
        "CMAKE_CXX_FLAGS": "-g -fno-omit-frame-pointer -fsanitize=address,undefined -isysroot /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk"
      }
    }
  ],
  "buildPresets": [
    { "name": "dev",  "configurePreset": "dev" },
    { "name": "asan", "configurePreset": "asan" }
  ]
}

    That -isysroot is not optional. Homebrew clang does not know where Xcode keeps the system headers, and without it the build dies inside <iostream>. JSON cannot run commands, so the path is written out literally — regenerate it with xcrun --show-sdk-path if you ever update Xcode.

  5. Configure and build both.

    cmake --preset dev   && cmake --build --preset dev
cmake --preset asan  && cmake --build --preset asan

    [ 50%] Building CXX object CMakeFiles/tests.dir/tests/main.cpp.o
[100%] Linking CXX executable tests
[100%] Built target tests

    Those two lines are clang++ -c and then the link step — the exact commands you typed by hand in Lesson 1, now typed for you. Run both:

    ./build/dev/tests     # 9
./build/asan/tests    # 9

  6. Add a .gitignore, then commit.

    echo "build/" > .gitignore
git add -A && git commit -m "Build system: two presets, warnings as errors"

Now see what the second build buys you

Introduce a classic off-by-one. In tests/main.cpp, change i < b.size() to i <= b.size() — one character. Then build and run both.

The everyday build:

cmake --build --preset dev && ./build/dev/tests
9

Exit code 0. It writes one int past the end of a heap allocation and reports nothing. That is undefined behaviour running silently, which is the single most dangerous state a C++ program can be in.

The sanitizer build, same source:

cmake --build --preset asan && ./build/asan/tests

==58506==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000100
WRITE of size 4 at 0x602000000100 thread T0
    #0 0x000104c49534 in main main.cpp:6

0x602000000100 is located 0 bytes after 16-byte region [0x6020000000f0,0x602000000100)
allocated by thread T0 here:
    #0 0x0001053d11f8 in _Znam  (libclang_rt.asan_osx_dynamic.dylib)
    #1 0x000104c49d1c in containers::Buffer::Buffer(unsigned long) vec.hpp:9
    #2 0x000104c49444 in main main.cpp:5

SUMMARY: AddressSanitizer: heap-buffer-overflow main.cpp:6 in main

Read what it gave you, because this is the report format you will live inside for the next four weeks:

  • What kind of bug — heap-buffer-overflow, and a WRITE not a read.
  • Where it happened — main.cpp:6.
  • How far out of bounds — 0 bytes after a 16-byte region. One element past the end of four ints.
  • Where the memory came from — a second stack trace pointing at vec.hpp:9, your constructor.

Both stack traces at once is the thing to appreciate. The bug is in the test; the allocation is in the library; ASan hands you both ends. Put the < back before moving on.

Also verify Prove -Werror is armed: add int unused = 7; to main and build. You should get error: unused variable 'unused' [-Werror,-Wunused-variable] and no executable. A warning you can ignore is a warning you will ignore, so the project refuses to build with any.

CheckRetrieval

  1. You edit vec.hpp. Which command do you run?

    • Configure, then build the preset
    • Only build the preset
    • Delete the build directory first

  2. You add a new target to CMakeLists.txt. What must happen?

    • Configure must run again
    • Nothing changes, just build
    • Both presets must be deleted

  3. Your header-only library sets a warning flag. Which keyword?

    • PRIVATE, kept to itself
    • PUBLIC, both directions
    • INTERFACE, consumers only

  4. Your ASan build passes clean. What has been proven?

    • The whole program is memory safe
    • The paths executed were memory safe
    • Every allocation was correctly freed

Say it out loud before revealing. Why does this project need two build directories rather than two sets of flags in one?

Because a build directory holds compiled object files, and these two builds use different compilers with different sanitizer runtimes. Object files from Apple clang and Homebrew clang must never be linked together, and CMake caches the compiler choice per build directory — a directory is configured for one compiler and cannot be re-pointed at another without wiping it. Separate directories make mixing them structurally impossible rather than merely unlikely.
