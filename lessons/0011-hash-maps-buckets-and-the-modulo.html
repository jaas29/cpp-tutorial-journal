Buckets, and the One Line That Makes It a Map

A hash map looks like a different kind of object from an array. It is not. It is an array, plus one line that turns a key into an index into it. Everything else in this lesson — chains, load factor, rehashing — exists to handle the fact that that line cannot be injective. Get the one line first, and the rest follows as damage control.

Knowledge 1An array you can index with a string

You already have a container you index with a number: v[3] goes straight to the fourth slot, one multiply and one add, no searching. That is the fastest lookup there is, and the only reason it is fast is that the index is the address arithmetic.

The whole idea of a hash map is to keep that, and buy your way into it from a key that is not a number:

index = hash(key) % bucket_count;     // a string goes in, a slot number comes out
table[index]                          // and now it is just an array access

That is it. That is the data structure. std::unordered_map, Java's HashMap, Python's dict — all of them are that line, plus decades of care about what happens when it goes wrong.

Knowledge 2std::hash, and why it is written with braces

You do not write the hash function. The standard library ships one for every built-in type and for std::string. But it is spelled oddly, and the spelling tells you what it is:

std::hash<K>{}(key)
//       ^^^  ^^ ^^^^^
//        |    |    the call
//        |    construct a temporary object of that type
//        the class template

std::hash<std::string> is a class, not a function. The {} default-constructs a nameless temporary, and then (key) calls that object's operator(). An object you can call like a function is a function object, or functor. The library uses a class rather than a plain function because a class can be specialized per type — which is exactly how you will teach it about your own types later, and how it already knows about std::string.

What comes out is a std::size_t, and on this machine it is enormous. Measured:

jose     14301728753766726926    % 8 = 6
roy      13235723348464347652    % 8 = 4
ada      10190926678592913505    % 8 = 1
grace    12564494891154384730    % 8 = 2
alan     13208046377741452544    % 8 = 0
cat       8210903754520128248    % 8 = 0

Two properties matter, and only two:

  • Deterministic. The same key always produces the same number, so you can find the value again. Without this the structure does not work at all.
  • Well spread. Similar keys should produce wildly different numbers. Look at ada and alan above: two characters in common, and nothing in common in the output. That spread is what keeps chains short.
One honest thing about std::hash<int>

Measured on this machine:

1 -> 1        42 -> 42        1000 -> 1000

It is the identity function. The standard permits this, and libc++ does it, because for most integer key sets it is both free and good enough. But it has teeth: it means the spread property above is entirely absent for int keys, and any structure in your keys survives into the bucket index. Insert the multiples of 8 into an 8-bucket table and every single one lands in bucket 0 — one chain, zero buckets used, a linked list wearing a hash map costume. This is a real, reproducible worst case, and it is the reason Lesson 12 will have something to say about choosing bucket_count. Note it now; do not fix it now.

Knowledge 3Collisions are the normal case

Look again at the table above. alan and cat both produce bucket 0. Two different keys, one slot. That is a collision, and the first instinct — treat it as an error, or pick a better hash to avoid it — is wrong on both counts.

It is wrong because it is arithmetically impossible to avoid. You are mapping an unbounded set of keys onto 8 slots. By the pigeonhole principle there is no hash function, however brilliant, that avoids collisions. And you do not need many keys before they are near-certain: with 8 buckets, the odds that 5 random keys all land in different buckets is about 21%. The question is never “how do I avoid collisions” but “what do I do when one happens,” and the answer defines your whole implementation.

The design decision, and how to defend it in review

Two families of answer, and you need to be able to say both:

Separate chainingOpen addressing
On collisioneach bucket holds a list of entries; append to itprobe forward to the next free slot; entries live in the one array
Memoryone allocation per bucket that gets usedone flat array, nothing else
Cache behaviourworse — following a chain jumps around memorybetter — probing reads adjacent memory
Eraseeasy — remove from the chainhard — a hole breaks later probes, so you need tombstones
At high loaddegrades gracefullydegrades sharply near full

Build separate chaining. Two reasons, and give them in this order if asked:

  1. Erase is correct by construction. Open addressing's tombstones are the classic source of a hash map that is subtly wrong for a long time before anyone notices — delete an entry, and a key whose probe sequence ran through that slot becomes unfindable. That is a bug you would rather not be hunting this week.
  2. It is what std::unordered_map does, and not by accident: the standard requires reference stability and bucket iteration, which effectively mandates chaining. So your comparison in the writeup is like-for-like, and where the standard library beats you it will be for reasons you can actually name rather than “different algorithm.”

And say the cost out loud, because it is the honest half: chaining is the slower of the two on modern hardware for lookup-heavy work, because chasing a chain is a cache miss and probing is not. The fast hash maps people reach for in production — absl::flat_hash_map, boost::unordered_flat_map — are open-addressed for exactly that reason. You are choosing correctness-under-time-pressure over throughput, deliberately, and that is a defensible engineering call as long as you are the one who says it first.

Build 1HashMap<K,V>, on top of your own Vector

The bucket array is a Vector, and each chain is a Vector. Your container from Weeks 1–2 is the substrate for the one in Weeks 3–4 — which is worth noticing, because it means everything you fixed in Lessons 6 through 10 is now load-bearing underneath this.

include/containers/hash_map.hpp — new file

#pragma once
#include <containers/vector.hpp>
#include <cstddef>
#include <functional>   // std::hash
#include <optional>

namespace containers
{
    template <typename K, typename V>
    class HashMap
    {
        struct Entry
        {
            K key{};        // the braces matter - see the note below
            V value{};
        };

        Vector<Vector<Entry>> m_buckets;   // one chain per bucket
        std::size_t m_size = 0;            // total pairs stored, not buckets used

    public:
        explicit HashMap(std::size_t bucket_count = 8)
        {
            for (std::size_t i = 0; i < bucket_count; ++i)
                m_buckets.push_back(Vector<Entry>{});
        }

        std::size_t size() const { return m_size; }
        std::size_t bucket_count() const { return m_buckets.size(); }

        std::size_t bucket_for(const K &key) const
        {
            return std::hash<K>{}(key) % m_buckets.size();
        }

        void insert(const K &key, const V &value)
        {
            Vector<Entry> &chain = m_buckets[bucket_for(key)];

            for (std::size_t i = 0; i < chain.size(); ++i)   // already present?
                if (chain[i].key == key)
                {
                    chain[i].value = value;                  // overwrite
                    return;                                  // m_size unchanged
                }

            chain.push_back(Entry{key, value});
            ++m_size;
        }

        std::optional<V> find(const K &key) const
        {
            const Vector<Entry> &chain = m_buckets[bucket_for(key)];
            for (std::size_t i = 0; i < chain.size(); ++i)
                if (chain[i].key == key)
                    return chain[i].value;
            return std::nullopt;
        }
    };
}

Four things in there are worth stopping on.

The & in Vector<Entry> &chain is load-bearing. Drop it and you get a copy of the chain; you then push into the copy, the copy is destroyed at the end of the function, and your insert silently does nothing. Your deep copy constructor from Lesson 7 would be working perfectly, and the bug would be entirely yours. This is the single most common way this header goes wrong.

const Vector<Entry> &chain in find is why Lesson 10 had to happen first. find is const, so m_buckets[...] calls your const operator[] and yields a const Vector<Entry>&, and then chain[i] needs a const operator[] too. Without yesterday's six lines this function does not compile at all.

K key{} rather than K key;. Lesson 9 Knowledge 4: new T[n] default-constructs every slot, so Entry must be default-constructible, and an uninitialised V value; for V = int would be an indeterminate value that UBSan will eventually catch you reading. The braces zero-initialize.

explicit on the constructor. Without it, HashMap<std::string,int> m = 8; compiles — the compiler would treat your constructor as an implicit conversion from size_t. explicit says this constructor may only be invoked deliberately. (Core Guidelines C.46: by default, declare single-argument constructors explicit.)

Knowledge 4std::optional, and what it costs you

“Find a key that might not be there” is the problem every language solves differently and most solve badly. Java returns null and you find out at runtime. C would return a pointer and you would hope the caller checks it.

std::optional<V> is a V and a bool, in one object, where the language will not let you reach the V without going past the bool:

    if (auto age = ages.find("jose"))      // converts to bool: was there a value?
        std::cout << *age;                 // only reachable inside the if

    if (!ages.find("nobody"))
        std::cout << "not found\n";

There is no null to forget. The check and the access are the same expression, and the value lives inside the optional itself — no separate allocation, no indirection.

Where the standard library wins, and put this in the writeup

std::unordered_map::find does not return an optional. It returns an iterator, and that is strictly more capable in two ways your version cannot match:

  • Yours returns a copy of the value. For int that is free; for a V that owns a megabyte, every lookup deep-copies a megabyte. An iterator refers to the stored value and copies nothing.
  • Yours is read-only. You cannot write through a copy, so m.find(k)->second = 5 has no equivalent, and neither does erase-what-you-found.

The syllabus asks for optional here, and it is the right teaching order — it is the version where the failure case is impossible to ignore. But know the trade, because “why does the real one return an iterator?” is exactly the question a reviewer asks, and “because mine copies the value and cannot mutate it” is the answer that shows you understood the choice rather than inherited it.

VerifyFive keys, one overwrite, one collision

    containers::HashMap<std::string, int> ages;
    ages.insert("jose", 21);
    ages.insert("roy", 45);
    ages.insert("ada", 36);
    ages.insert("grace", 85);
    ages.insert("alan", 41);
    ages.insert("jose", 22);        // overwrite - must NOT become a sixth entry

jose -> 22
nobody -> not found

Then force the collision, because the distribution above never hit one and an untested branch is an untested branch — that is the lesson of the last three blocks. Insert alan and cat, which the table in Knowledge 2 shows both hash to bucket 0. Under the asan preset (ASan + UBSan, Homebrew clang):

size 2
bucket 0 chain length 2
alan -> 41
cat  -> 9
exit 0, no sanitizer report

Two entries, one bucket, both retrievable. That is chaining working. Add a chain_length(std::size_t) accessor to see it — it is a debugging window into the structure, and you will want it again in Lesson 12 when the load factor starts mattering.

SkillRetrieval

  1. Why is it std::hash<K>{}(key) and not std::hash(key)?

    • The braces initialize the key
    • It avoids an extra header
    • The type cannot be deduced
    • It is a class, not a function

  2. Why can no hash function avoid collisions?

    • The modulo discards high bits
    • More keys than available slots
    • Hashes must stay cheap enough
    • Keys are compared by equality

  3. What breaks if chain is not a reference?

    • Inserts vanish into a copy
    • The bucket index goes stale
    • Two entries share one slot
    • The chain is freed too early

  4. What does returning optional<V> cost you?

    • A heap allocation per lookup
    • The ability to store nulls
    • Copies, and cannot mutate
    • Constant-time average lookup

  5. What is std::hash<int> on this machine?

    • A multiply-and-shift mix
    • The identity, unchanged
    • A cryptographic digest
    • A seeded random permutation

Out loud, as if Prof. Roy asked in review: you chose separate chaining. Defend it, and say what you gave up.

Chaining makes erase correct by construction — open addressing needs tombstones, and a deleted slot that breaks a later probe sequence is a subtle, long-lived bug I did not want to be hunting in a four-week project. It is also what std::unordered_map does, effectively mandated by the standard's reference-stability and bucket-iteration requirements, so my benchmark compares like with like. What I gave up is throughput: following a chain is a cache miss where probing reads adjacent memory, which is why the fast production maps — absl::flat_hash_map, boost::unordered_flat_map — are all open-addressed. I traded lookup speed for correctness under a deadline, on purpose.
