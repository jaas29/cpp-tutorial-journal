The Copy Constructor, and Deep Copy

Lesson 6 ended with a stopgap: Vector(const Vector&) = delete;, which turns a silent abort into a compile error. That was the right thing to commit at 11pm. It is not the right thing to hand in. This lesson replaces it with the real answer — and then shows you a bug in the standard version of that answer, measured on your machine, that no sanitizer you own can see.

Knowledge 1One buffer versus two

The crash in Lesson 6 was not really about destructors. It was about the word copy meaning two different things, and the compiler picking the wrong one.

  • A shallow copy duplicates the members. m_data is a pointer, so duplicating it duplicates an address. One buffer, two owners, two frees.
  • A deep copy duplicates what the members point at. Two buffers, holding equal values, each owned by exactly one object.

The compiler-generated copy constructor always does the shallow one. It cannot do otherwise: it knows m_data is an int*, but nothing in the type says whether that pointer owns the memory or merely refers to memory somebody else owns. Both are legal and common. Ownership is a fact about your design, not about the type, so it is your job to state it — and the way you state it is by writing these functions.

Knowledge 2The signature, and the two ways to get it wrong

A copy constructor is a constructor whose one parameter is a reference to its own type:

Vector(const Vector& other)

Both halves of that parameter are load-bearing, and both failures are compile errors you can produce on purpose in ten seconds. Do produce them — an error you have seen once costs a minute later, and an error you have never seen costs an afternoon.

Take it by reference, not by value. Vector(Vector other) would mean “to copy a Vector, first copy a Vector into the parameter” — infinite recursion, before the body ever runs. The compiler refuses outright rather than letting you write it:

vector.hpp:59:23: error: copy constructor must pass its first argument by reference
   59 |         Vector(Vector other)
      |                       ^
      |                       const &

Take it by const reference. Dropping the const compiles — and that is the trap, because Vector b = a; keeps working. It breaks later, the first time you copy something you promised not to modify, which in practice is the first time you pass a Vector to a function as const Vector&:

error: no matching constructor for initialization of 'containers::Vector'
    2 | containers::Vector duplicate(const containers::Vector &v) { containers::Vector copy = v; ...
      |                                                                                ^      ~
note: candidate constructor not viable: 1st argument ('const containers::Vector')
      would lose const qualifier
   59 |         Vector(Vector &other)

Copying does not modify the source, so promise that in the signature. That promise is what lets callers hand you a const object at all.

One member you must not copy blindly

Copy m_size elements, not m_capacity. The slots between m_size and m_capacity were allocated but never written — new int[8] leaves them uninitialized, and reading an uninitialized int is undefined behaviour, even if all you do with the value is copy it somewhere else. The new buffer’s tail is uninitialized too, which is fine: nothing is allowed to read past m_size either.

Build 1The copy constructor

In include/containers/vector.hpp, delete the line Vector(const Vector &) = delete; and put this in its place. Leave the copy assignment = delete alone for one more minute — it is the next build step, and the two are different jobs.

include/containers/vector.hpp — below ~Vector()

        // Copy constructor: build a NEW Vector that duplicates other.
        // Called by `Vector b = a;` and whenever a Vector is passed or returned by value.
        // There is no existing buffer to release here - this object does not exist yet.
        Vector(const Vector &other)
            : m_data(new int[other.m_capacity]),   // our own buffer, same capacity
              m_size(other.m_size),
              m_capacity(other.m_capacity)
        {
            // Copy the live elements only. Slots past m_size were never written,
            // and reading uninitialized ints is UB even just to copy them.
            for (std::size_t i = 0; i < m_size; ++i)
                m_data[i] = other.m_data[i];
        }

The : m_data(...), m_size(...) part before the body is a member initializer list. It initializes each member directly, in the order the members are declared in the class — not the order you write them here. Getting those two orders out of sync is the classic source of a member being read before it is set, and -Wall (which your presets already carry as -Werror) warns about it. Yours match: m_data, m_size, m_capacity.

Now exercise it. In tests/main.cpp, the three lines from Lesson 6 that used to abort:

containers::Vector b = a;    // copy constructor
b[0] = 999;
std::cout << "a[0] = " << a[0] << "   b[0] = " << b[0] << "\n";
$ ./build/asan/tests
a[0] = 0   b[0] = 999

a did not move. That one line of output is the whole lesson: last time it read a[0] = 999 and then the process died. Two buffers now, and the aliasing is gone with the crash.

Knowledge 3Assignment is a different job

These two lines look like the same operation and are not:

containers::Vector b = a;   // construction  - calls the copy CONSTRUCTOR
c = a;                      // assignment    - calls copy ASSIGNMENT

The = in the first line is not assignment at all; it is initialization syntax for an object that does not exist yet. The distinction is not pedantry, because it changes the work required. The copy constructor starts from nothing, so it only has to acquire. Copy assignment starts from a c that is already alive and already owns a buffer. If it only acquires, the old buffer leaks.

So assignment has five steps where construction had one:

Vector& operator=(const Vector& other) {
    if (this == &other) return *this;       // 1. self-assignment early-out
    int* fresh = new int[other.m_capacity];  // 2. allocate BEFORE releasing
    for (std::size_t i = 0; i < other.m_size; ++i)
        fresh[i] = other.m_data[i];          // 3. copy into the new buffer
    delete[] m_data;                         // 4. only now release the old
    m_data = fresh; m_size = other.m_size; m_capacity = other.m_capacity;
    return *this;                            // 5. always, for chaining
}

Three things worth naming:

  • this is a pointer to the object the member function was called on. It is how a member function refers to itself, and *this is the object.
  • Returning Vector& is what makes x = y = z work, and matches what every built-in type does. Returning by value would copy again for nothing.
  • Allocate before you release. If new throws — and it can, std::bad_alloc — the object still holds its original, intact buffer. Free first and a throw leaves you holding a dangling pointer, in an object whose destructor is still going to run.

Build 2Copy assignment, and a test you cannot write

Replace Vector &operator=(const Vector &) = delete; with the real one, and delete the now-stale comment above the pair. Then exercise it — note that c must already own a buffer, or you are not testing the interesting half:

containers::Vector c;
c.push_back(7);              // c now owns a 1-element buffer of its own
c = a;                       // copy assignment: that buffer must be released
std::cout << "c[0] = " << c[0] << "  size " << c.size()
          << "  cap " << c.capacity() << "\n";
$ ./build/asan/tests
a[0] = 0   b[0] = 999
c[0] = 0  size 5  cap 8

Then test self-assignment — and here your own build settings stop you:

$ ./build/dev/tests
main.cpp:18:7: error: explicitly assigning value of variable of type 'containers::Vector'
               to itself [-Werror,-Wself-assign-overloaded]
   18 |     c = c;
      |     ~ ^ ~

That is your -Werror from Lesson 2 firing, correctly: literal c = c; in real code is always a mistake, so clang refuses it. Write the test through a reference, which is also how self-assignment actually reaches you in production — two names for one object, arrived at through parameters:

containers::Vector &alias = c;
c = alias;                   // self-assignment, invisible to the compiler
std::cout << "after self-assign c[3] = " << c[3] << "\n";   // 30

Then all three builds, because by now you know that no one of them is a proxy for “clean”:

$ ./build/dev/tests                 # UBSan
a[0] = 0   b[0] = 999
c[0] = 0  size 5  cap 8
after self-assign c[3] = 30

$ ./build/asan/tests                # AddressSanitizer - no report
$ /usr/bin/clang++ -std=c++20 -g -Iinclude tests/main.cpp -o /tmp/leakcheck
$ MallocStackLogging=1 leaks -atExit -- /tmp/leakcheck
Process 25119: 0 leaks for 0 total leaked bytes.

Three copies alive, three buffers, three destructors, zero leaked bytes. Commit this: it is the ownership half of the Sep 2 deliverable.

Knowledge 4What the guard actually buys — measured

Every textbook opens copy assignment with the self-assignment guard, and the usual justification is: without it, v = v frees the buffer and then copies out of the memory it just freed. That reasoning describes a different function than the one above. It is worth seeing why, because it is the difference between memorizing a ritual and knowing a mechanism.

Both variants were built and run on this machine today. Same test, same compilers:

OrderingGuardc[3] after self-assignSanitizers
allocate → copy → releaseyes30 — correctsilent
allocate → copy → releaseno30 — correctsilent
release → allocate → copyyes30 — correctsilent
release → allocate → copyno-1094795586silent

Read the middle two rows together and the real rule appears: the ordering is the fix, and the guard is an optimization. Allocate-before-release makes self-assignment correct on its own, because at the moment you copy, the source buffer has not been touched. The guard's job is to skip a pointless allocate-and-copy of an object onto itself — worth having, not what is holding the function up. Reverse the ordering and the guard becomes the only thing standing between you and row four.

Row four is the one to look at hardest. -1094795586 is 0xBEBEBEBE, AddressSanitizer’s fill pattern for freshly allocated memory. That is the tell: after delete[] m_data, the loop copies from other.m_data — but other is *this, so other.m_data now names the new buffer, and the function copies uninitialized memory onto itself. Your data is gone and the program keeps running.

Why nothing caught it

Not a use-after-free — the read is from the new buffer, which is live. ASan tracks memory that is freed or out of bounds; this is neither. Reading uninitialized memory is a different detector (MemorySanitizer), which does not exist on Darwin/arm64. UBSan does not cover it. It leaks nothing.

So add a fourth line to the triage table from record 0007: dev is silent on heap corruption, asan is silent on leaks, and all three builds are silent on reading uninitialized memory. The only detector for that class is an assertion in a test — which is the argument for writing the checks in tests/main.cpp as something that fails loudly rather than something you read with your eyes.

SkillRetrieval

  1. Which function does Vector b = a; call?

    • The copy assignment operator
    • The default constructor first
    • The copy constructor, always
    • Neither, the compiler elides

  2. What must assignment do that construction need not?

    • Copy every element across
    • Release the buffer already held
    • Allocate a brand new buffer
    • Promise not to modify other

  3. Why must the parameter be a reference, not a value?

    • References are cheaper to pass
    • Values cannot be marked const
    • The buffer would be shared
    • Copying it would call itself

  4. Allocating before releasing makes the guard into what?

    • An optimization, not a fix
    • A required correctness check
    • A guard against leaked bytes
    • An error under -Werror rules

  5. How many elements does the copy loop read?

    • Exactly m_capacity elements
    • Exactly m_size elements
    • Capacity minus size elements
    • Whichever of them is larger

Out loud: name the five steps of copy assignment in order, and say which one the copy constructor does not need and why.

Guard against self-assignment; allocate the new buffer; copy the elements into it; release the old buffer; assign the members and return *this. The copy constructor skips the release, because the object it is building did not exist a moment ago and therefore owns nothing yet.
