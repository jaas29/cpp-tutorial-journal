Four Programs, Not One

When you type clang++ main.cpp, four different programs run in sequence. Each fails in its own way. Today you take the pipeline apart by hand, and learn to name which of the four is the one complaining.

Why this, firstThe build is the thing you will fight most

You are about to write a vector from scratch. That is a header-heavy, multi-file, template-heavy project, and the errors it produces will be long. The single skill that separates people who enjoy that from people who suffer through it is reading the error at the right layer.

An error that says file not found is not the same kind of problem as one that says no matching function, which is not the same kind of problem as Undefined symbols — even though all three come out of the same clang++ command. They come from three different programs, which know three different amounts about your code. That is the whole lesson.

Mission link Your success criteria include reading a failure and knowing what kind of failure it is before reaching for a debugger. This is that same habit, one level earlier: before the program can crash, it has to build, and build failures have their own taxonomy.

KnowledgeThe pipeline

C++ compiles one file at a time, in total isolation. This is the fact that explains almost everything else about the language's file layout. The compiler working on main.cpp has no idea that add.cpp exists.

The four programs, and what each one knows:

ProgramJobKnows about
Preprocessor Textual find-and-replace. Pastes each #included file in wholesale, expands macros, drops #if branches that don't apply. Text. Not C++. It has no idea what a function is.
Compiler Parses and type-checks one translation unit, then emits assembly for it. One .cpp plus everything it included. Nothing else in your project.
Assembler Turns that assembly text into machine code in an object file. Almost nothing. It rarely fails on you.
Linker Collects all object files and libraries, matches every use of a name to exactly one definition, writes the executable. Names and addresses. Not types, not your source code.

The output of the preprocessor has a name you will see in error messages and in the standard: a translation unit. learncpp puts it exactly this way: "When the preprocessor has finished processing a code file, the result is called a translation unit" — one .cpp file plus every header it pulled in, recursively (learncpp 2.10).

The division of labour that matters

A declaration is a promise that a name exists somewhere: int add(int x, int y);. A definition is the thing itself, with a body. The compiler is satisfied by promises. The linker is the one that collects the debts.

That is why a missing function body is not a compiler error. The compiler saw the promise, believed you, and emitted a call to a name it assumed would show up later. Only the linker finds out that nobody ever provided it — and it says so with Undefined symbols, per learncpp 2.8.

SkillRun the pipeline by hand

Do this now, in a scratch directory — not in this workspace, and not in your project repo. Something like ~/Projects/scratch/pipeline. Three files:

add.h

#pragma once
int add(int x, int y);   // declaration: a promise

add.cpp

#include "add.h"
int add(int x, int y) { return x + y; }   // definition: the real thing

main.cpp

#include <iostream>
#include "add.h"

int main() {
    std::cout << add(2, 3) << '\n';
}

Now stop each stage in turn and look at what came out. The flags are the point here: each one says "run the pipeline, then halt".

  1. Stop after the preprocessor (-E) and see how much text one #include actually drags in:

    clang++ -std=c++20 -E main.cpp | wc -l

    On my machine: 93,524 lines. You wrote six. That is what #include <iostream> costs, and it is why C++ builds are slow. Now try the small one, where you can read the whole output:

    clang++ -std=c++20 -E -P add.cpp

    int add(int x, int y);
int add(int x, int y) { return x + y; }

    The #include "add.h" line is gone, replaced by the file's contents. That is literally all the preprocessor did. -P just suppresses line-number bookkeeping so the output is readable.

  2. Stop after the compiler (-S) and read the assembly for add:

    clang++ -std=c++20 -S -O1 add.cpp -o add.s

    The interesting three lines, on arm64:

    __Z3addii:
    add  w0, w1, w0
    ret

    Your function is one instruction. Note the name it was given: __Z3addii — that is add taking (int, int), encoded. C++ allows overloading, so the compiler mangles the types into the symbol name to keep the overloads distinct. Hold onto that; it explains a nasty error in a moment.

  3. Stop after the assembler (-c) to get object files, and inspect their symbol tables with nm:

    clang++ -std=c++20 -c add.cpp -o add.o
clang++ -std=c++20 -c main.cpp -o main.o
nm add.o
nm -u main.o | head -3

    $ nm add.o
0000000000000000 T __Z3addii        <- T = defined here, in the Text section

$ nm -u main.o
__Unwind_Resume
__Z3addii                           <- -u = undefined: a hole to be filled
...

    This is the whole linking model, visible. add.o has the symbol. main.o has a hole with the same name. Neither file knows about the other.

  4. Link, and run:

    clang++ add.o main.o -o prog
./prog          # 5

    The linker matched the hole to the symbol. Nothing more mysterious than that.

Note clang++ main.cpp add.cpp -o prog does all four stages for both files in one go, and is what you will actually type day to day (until CMake types it for you). You just did it the long way once so that the short way stops being magic.

Break it on purpose

Now cause each failure deliberately. This is the part worth doing slowly — you are building an error-message-to-stage lookup table in your head, and the only way to get it is to see the real text.

  1. In main.cpp, change the include to #include "adder.h". Build. Undo.
  2. Restore it, then change the call to add(2). Build. Undo.
  3. Restore it, then link main.o alone: clang++ main.o -o bad.
  4. Restore it, then change only add.cpp's definition to int add(int x, long y), leaving add.h as it was. Compile both files, then link them.

That last one is the trap. Both files compile without a single complaint — add.cpp just thinks it defined an unrelated overload — and then:

Undefined symbols for architecture arm64:
  "add(int, int)", referenced from:
      _main in main.o

Because nm on that object file now shows __Z3addil (…int, long), not __Z3addii. A declaration and definition that disagree produce two different mangled names, so the failure lands at link time, in a message that names neither file you edited. When you hit this for real in a header-plus-source pair, it will not look obvious. Now it will.

  4. add.h declares int add(int, int). add.cpp includes that header but defines int add(int, long). main.cpp calls add(2, 3). Where does the build first fail?

    • The preprocessor
    • The compiler
    • The linker

Say it out loud before revealing. Why does the compiler accept a call to a function whose body does not exist anywhere in your project?

Because it compiles one translation unit in isolation and has no way to see the rest of the project. A declaration is a promise that some other translation unit will provide the definition; the compiler emits a call to that name and leaves a hole. Only the linker, which sees every object file at once, can tell whether the promise was kept.
