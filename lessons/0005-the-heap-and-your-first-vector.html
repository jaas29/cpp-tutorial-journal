The Heap, and Your First Vector

Three lessons on the build system is enough. This one ends with a Vector that grows — about forty lines, and the first code in this project that is actually Project 1. It will also contain a memory leak, on purpose, which you will then find with a tool rather than by staring.

Knowledge 1Two places a variable can live

Every value in a C++ program lives in one of two places, and the difference is the whole reason vector has to exist.

The stack is where local variables go. When you write int x = 5; inside a function, the compiler already knows, at compile time, how many bytes that needs and exactly where to put them. Entering a function moves a pointer down; leaving it moves the pointer back up, and everything that was there is gone. That is why it is fast, and it is why the size has to be known in advance.

The heap is a large pool you request memory from at runtime, in whatever size you compute while running. Nothing releases it automatically. It stays yours until you say otherwise.

Knowledge 2The Java shift

This is flagged in your proposal as the single most important conceptual shift, so it is worth being blunt about it.

In Java, Vector v is a reference. The object is always on the heap, the variable is a handle pointing at it, and assignment copies the handle. Two variables, one object. Garbage collection decides when it dies.

In C++, Vector v is the object. It sits in the stack frame. Assignment copies the object. Two variables, two objects. It dies at the closing brace of its scope, at a moment you can point to in the source.

Knowledge 3Asking for heap memory

Two operators, and they come in matched pairs:

int* p = new int[8];   // allocate 8 ints on the heap; p holds their address
p[3] = 42;             // use it exactly like an array
delete[] p;            // give it back
p = nullptr;           // p no longer points anywhere valid; say so
  • new int[8] returns a pointer — a variable holding an address. int* is read as “pointer to int.”
  • new[] pairs with delete[], and plain new pairs with plain delete. Crossing them is undefined behaviour, not a warning.
  • The 8 does not need to be a constant. That is the entire point — this is the only way to get a buffer whose size you compute while running.
Yes, this is the “old” style Your mission bans raw new/delete as a default, and that stands. But inside a container you are the one implementing the safety that everyone else gets to use. std::vector does exactly this internally. Writing it by hand here is the point; carrying it into Projects 2 and 3 is the mistake.

BuildVector, forty lines

Write this yourself rather than pasting it. This is Project 1 work, so it goes in the P1 repo — ~/projects/p1-containers, not the mystl scratch repo. Put it in include/containers/vector.hpp, alongside the existing vec.hpp.

Leave Buffer alone include/containers/vec.hpp already holds Buffer, a fixed-size type that frees itself in its destructor. Do not extend it and do not delete it. Vector is a separate class in a separate header, and the whole point of this lesson is that it does not have that destructor yet.

include/containers/vector.hpp

#pragma once
#include <cstddef>

namespace containers {

class Vector {
    int* m_data = nullptr;    // the heap buffer, or nullptr if we have none yet
    std::size_t m_size = 0;   // how many values the user has put in
    std::size_t m_cap  = 0;   // how many slots we allocated

public:
    void push_back(int value) {
        if (m_size == m_cap) grow();
        m_data[m_size] = value;
        ++m_size;
    }

    int& operator[](std::size_t i) { return m_data[i]; }

    std::size_t size()     const { return m_size; }
    std::size_t capacity() const { return m_cap; }

private:
    void grow() {
        std::size_t new_cap = (m_cap == 0) ? 1 : m_cap * 2;
        int* fresh = new int[new_cap];                 // 1. bigger buffer
        for (std::size_t i = 0; i < m_size; ++i)       // 2. copy the old values
            fresh[i] = m_data[i];
        delete[] m_data;                               // 3. release the old buffer
        m_data = fresh;                                // 4. adopt the new one
        m_cap = new_cap;
    }
};

} // namespace containers

Four steps in grow, in that order. Getting them out of order — deleting before copying, most commonly — is the classic version of this bug, and it reads perfectly fine.

Why doubling rather than adding one? Because copying is the expensive part. Doubling means n pushes cost n copies in total rather than n²/2. You will be asked this in review; the answer is amortised constant time, and it is a real reason, not a convention.

Drive it from tests/main.cpp:

#include <containers/vector.hpp>
#include <iostream>

int main() {
    containers::Vector v;
    for (int i = 0; i < 5; ++i) {
        v.push_back(i * 10);
        std::cout << "size " << v.size() << "  cap " << v.capacity() << "\n";
    }
    std::cout << v[3] << "\n";
}

Build and run it with the dev preset:

$ cmake --build --preset dev
$ ./build/dev/tests
-Werror is on in P1 Unlike the scratch repo, CMakeLists.txt here compiles with -Wall -Wextra -Wpedantic -Werror. A signed/unsigned comparison or an unused variable is a build failure, not a yellow squiggle. That is deliberate. Fix the warning; do not silence the flag.

That prints:

size 1  cap 1
size 2  cap 2
size 3  cap 4
size 4  cap 4
size 5  cap 8
30

Watch the capacity column: it jumps only when it has to, and size 4 costs no allocation at all. That is the doubling paying off.

The bugYou just leaked, and ASan will not tell you

Nothing in that class ever calls delete[] on the final buffer. When v goes out of scope its three members vanish — including m_data, the only record of where the heap buffer was. The buffer is still allocated and now unreachable. That is a leak.

Here is the part worth knowing about your machine specifically: AddressSanitizer does not detect leaks on macOS. LeakSanitizer is not available on Darwin, so your asan build runs this program and reports nothing. Use Apple’s leaks tool instead. Wrap the vector in a scope so it is destroyed before the program ends, then:

$ MallocStackLogging=1 leaks -atExit -- ./build/dev/tests

Process 44701: 1 leak for 48 total leaked bytes.

STACK OF 1 INSTANCE OF 'ROOT LEAK: <malloc in containers::Vector::grow()>':
5   tests       main + 72                                   main.cpp:8
4   tests       containers::Vector::push_back(int) + 56     vector.hpp:13
3   tests       containers::Vector::grow() + 104            vector.hpp:26
2   libc++abi   operator new(unsigned long) + 52
1   libsystem_malloc  _malloc + 96

That is real output from this machine, and it names the line that allocated. Your line numbers will differ; the frames will not. 48 bytes: the 8-slot buffer, times four bytes per int, plus allocator overhead.

Read the stack from the bottom up and it is the whole call chain: main called push_back, which called grow, which called new[]. The leak is blamed on grow because that is where the surviving buffer was allocated — the allocation site, not the place you forgot to free. Leak tools always report it this way, because the forgetting has no location.

The fix is one function, and it is the subject of the next lesson: a destructor, and the idea called RAII that grows out of it.

SkillRetrieval

  1. In int main() { containers::Vector v; ... }, where does v itself live?

    • On the heap, like in Java
    • On the stack, in the frame
    • Half on each, split evenly
    • Nowhere until you push

  2. Inside grow, which ordering mistake produces a use-after-free?

    • Setting capacity before size
    • Allocating before you copy
    • Deleting before you copy
    • Adopting before you delete

  3. Doubling capacity instead of adding one slot buys you what?

    • Less memory used overall
    • Pointers that stay valid
    • Fewer bytes per element
    • Constant time per push

  4. Your asan build runs the leaking program. What does it report?

    • Nothing; no leak checking
    • A leak, with the alloc site
    • A leak, without any stack
    • A crash at the leaking line

Out loud: why can a stack variable not hold a buffer whose size you only learn at runtime?

Stack layout is decided at compile time — the compiler emits a fixed frame size. A runtime-sized buffer has no compile-time size, so it must come from the heap.
