The Destructor, and the Bug It Creates

Lesson 5 left a leak in Vector on purpose. Fixing it takes one line. The interesting part is what happens next: that one line converts a leak that nothing on your machine could see into a crash that aborts the program. Both bugs were always there. The destructor only made one of them loud.

Knowledge 1A function that runs when the brace closes

In Lesson 5 you saw the C++ side of the Java table: Vector v; is the object, it lives in the stack frame, and it dies at the closing brace of its scope — at a moment you can point to in the source.

C++ lets you attach code to that moment. A destructor is a member function named ~ClassName, taking no arguments and returning nothing, that the compiler calls automatically when the object is destroyed. You never call it yourself.

~Vector() { delete[] m_data; }

Three things about it that are not obvious:

  • It runs on every exit from the scope — falling off the end, an early return, or an exception unwinding through. There is no path out of the block that skips it. This is the property that makes it trustworthy in a way a delete[] you wrote by hand at the bottom of the function is not.
  • It runs on the object, not on the buffer. v’s three members are reclaimed by the stack pointer moving regardless; the destructor exists so that the heap buffer m_data points at gets released too.
  • delete[] nullptr is defined and does nothing. So a Vector that was never pushed to destroys itself correctly with no special case.

Knowledge 2RAII, and why it has a bad name

The pattern has a name you will hear constantly: RAII, Resource Acquisition Is Initialization. It is a famously unhelpful name, because the half that matters is the release, not the acquisition. Read it as: tie the lifetime of a resource to the lifetime of an object, so that scope exit does the cleanup.

The resource does not have to be memory. The same shape covers a file handle, a mutex lock, a socket, a database connection. Acquire in the constructor, release in the destructor, and then the only thing you have to get right is the object’s scope — which the language already enforces.

This is the answer to “where is the garbage collector?” Java frees memory eventually, at a time nobody chooses, and has nothing to say about your file handles. C++ frees everything at a point in the source you can name, deterministically. That determinism is the feature, and it is bought entirely with destructors. When your mission says raw new/delete is banned outside a container, RAII is what replaces it: std::vector, std::unique_ptr and friends are all just this lesson, written once by somebody else.

Build 1One line, and the leak is gone

In ~/projects/p1-containers/include/containers/vector.hpp, add a destructor to Vector. It goes inside the class body — at the top of the existing public: block, above push_back. Constructors and the destructor conventionally come first, because they are what a reader looks for when asking what a type owns.

include/containers/vector.hpp — inside class Vector { ... };

    public:
        // Releases the buffer this Vector owns. Runs automatically at scope exit,
        // on every path out - including an exception unwinding through.
        // delete[] on nullptr is defined and does nothing, so a Vector that was
        // never pushed to needs no special case.
        ~Vector() { delete[] m_data; }

        // Append one value to the end.
        void push_back(int value)
        ...

You do not need a second public:. An access specifier stays in effect until the next one, so the block opened before push_back already covers this.

If you get error: expected unqualified-id on the word public

You have put the destructor below the class’s closing }; rather than inside it, so it landed at namespace scope. public: is an access specifier, and access control is a property of a class — a namespace has none, so the keyword cannot legally begin a declaration there. The braces still balance, which is why the error appears at public and not at the real culprit, the }; now sitting above your new code.

The destructor underneath it would be wrong for a second reason too: ~Vector is only a destructor when declared inside the class it destroys, and m_data outside the class refers to nothing, because there is no object to read it from.

Then delete the NOTE: comment at the bottom of the file about the deliberate leak. It is no longer true, and a stale comment is worse than no comment.

Now prove it. Remember from record 0006 that neither preset can see leaks — asan because LeakSanitizer does not exist on Darwin, dev because UBSan hides the allocation from leaks. So leak checking needs its own unflagged build. Your existing tests/main.cpp needs no changes: -atExit runs the analysis after main has returned, so a Vector declared directly in main has already been destroyed by the time leaks looks.

$ /usr/bin/clang++ -std=c++20 -g -Iinclude tests/main.cpp -o /tmp/leakcheck
$ MallocStackLogging=1 leaks -atExit -- /tmp/leakcheck

Process 17726: 188 nodes malloced for 32 KB
Process 17726: 0 leaks for 0 total leaked bytes.

Compare that to Lesson 5’s 1 leak for 48 total leaked bytes. Same program, one extra function. Commit this.

Make the test prove something

0 leaks is only evidence if the same check would have said 1 leak without your fix. A test that passes for the wrong reason is worse than no test, and leak checking on this machine has already produced two of those (records 0005 and 0006).

So verify the verifier: temporarily empty the destructor body, rebuild, rerun. You should get ROOT LEAK: <malloc in containers::Vector::grow()>, 48 bytes. Put the delete[] back and it returns to zero. Now the zero means something.

The new bugNow copy it

Add three lines to tests/main.cpp. Nothing here looks dangerous:

containers::Vector a;
for (int i = 0; i < 5; ++i) a.push_back(i * 10);

containers::Vector b = a;    // copy
b[0] = 999;
std::cout << "a[0] = " << a[0] << "\n";

You did not write a copy constructor, so the compiler wrote one for you. Its rule is simple and, here, catastrophic: copy each member. m_size and m_cap copy fine. m_data is a pointer, so copying it copies the address — not what it points at. Two Vector objects, one buffer, and each of them believes it owns it.

Build it with the dev preset first, because what you get is worth seeing:

$ ./build/dev/tests
$ echo $?
133

No message. Nothing on stderr, and not even the a[0] = ... line, because the process is killed before stdout is flushed. Exit 133 is 128 + 5, meaning the process died on signal 5. That is the entire diagnostic. Two days before a checkpoint, that is the kind of failure that eats an evening.

Note the last line too: a[0] = 999. You wrote to b and a changed. That is the Java aliasing behaviour from Lesson 5’s table, showing up in C++ by accident — and it is a bug in its own right, independent of the crash.

Stop the bleeding today

The real fix is a copy constructor that allocates its own buffer — that is the next lesson, and it is checkpoint material. Until you write it, make the compiler refuse the copy rather than silently producing a broken one:

Vector() = default;                        // see below - not optional
Vector(const Vector&) = delete;
Vector& operator=(const Vector&) = delete;

Vector() = default; is required, and leaving it out is the next error you will hit. The compiler generates a default constructor for you only while you have declared no constructor at all. Vector(const Vector&) = delete; is a declaration — deleting a function still declares it — so adding it removes the zero-argument constructor that containers::Vector a; has been calling since Lesson 5:

error: no matching constructor for initialization of 'containers::Vector'
    6 |     containers::Vector a;
note: candidate constructor not viable: requires 1 argument, but 0 were provided
   56 |         Vector(const Vector &) = delete;

= default asks for the one the compiler would have written anyway. With it in place, Vector b = a; is a compile error naming the deleted function, instead of a runtime abort with no message. A non-copyable type is a legitimate design choice, not a placeholder hack — std::unique_ptr is exactly this. Commit it, and delete the two lines when the real copy constructor lands.

Knowledge 3The rule this is an instance of

Once a class has a destructor that does real work, it owns something, and the compiler-written copy operations are almost certainly wrong for it. The Rule of Three (C++98) says: if you write any of the destructor, copy constructor, or copy assignment operator, you probably need all three. C++11 adds move construction and move assignment, making it the Rule of Five.

You have just written one of the five. That is exactly why a bug appeared — and then a second one, at compile time, when the = delete stopgap took your default constructor away. Neither was a mistake in what you typed. Both are the same mechanism: declaring any one of these functions changes what the compiler generates for the others, with no warning.

You declareCompiler silently stops generatingYou find out
any constructorthe default constructorCompile error — the good case
a destructorboth move operationsNever. Your moves become copies.
a copy constructorboth moves, and the default constructorHalf at compile time, half never

That entanglement is the real argument behind Core Guideline C.21 — not tidiness. The card with all five, when the compiler generates each, and what each one has to do, is on the new reference sheet: Ownership and the Rule of Five. That sheet is the map for the rest of Project 1.

SkillRetrieval

  1. Which exit from a scope skips the destructor?

    • An exception thrown inside
    • An early return statement
    • Falling off the closing brace
    • None of these skip it

  2. Why does Vector b = a; now crash?

    • The buffer is too small
    • Both objects free one buffer
    • Vector has no constructor
    • Copying resets the capacity

  3. On the double free, what did the dev build report?

    • A symbolized double-free stack
    • A warning at compile time
    • Nothing beyond exit code 133
    • A leak of thirty-two bytes

  4. The Rule of Three says writing one of them means what?

    • You likely need all three
    • You should delete the rest
    • The class cannot be copied
    • The compiler writes no more

Out loud, in one sentence each: what does RAII tie together, and what does the compiler’s copy constructor do to a pointer member?

RAII ties the lifetime of a resource to the lifetime of an object, so that scope exit releases it on every path out. The generated copy constructor copies each member, so a pointer member is copied as an address — two objects, one buffer, two frees.

Read this one first. Everything above is the mechanism; this is the authority.
