Iterators, and the Crash That Names Its Own Cause

The Sep 2 checkpoint asked for “iterators that work with STL algorithms.” That sounds like a class you have to write. It is six lines, and four of them are return. The reason it takes a lesson anyway is the second half: those same six lines let you reproduce iterator invalidation on demand, and read a sanitizer report that points straight at grow(). Your mission says you want to look at a crash and know which of three bugs it is. This is you manufacturing one of the three on purpose.

Knowledge 1An iterator is not a type. It is a set of operations.

This is the first place your Java instincts will actively mislead you. In Java, Iterator is an interface: a named thing with hasNext() and next(), and your class implements it or it does not.

C++ has no such interface. An iterator is anything that supports the operations the algorithm uses. std::sort does not ask “do you implement Iterator?” — it is a template, so it simply writes *it, ++it, it != last, it + n into its body and lets the compiler find out whether those compile for your type. If they do, you are an iterator. Nobody registered anything.

Now look at what a raw T* already supports:

The algorithm writesOn a T* this meansWorks?
*itdereference the pointeryes, built in
++itadvance by sizeof(T) bytesyes, built in
it != lastcompare two addressesyes, built in
it + n, it - firstpointer arithmeticyes, built in

A raw pointer is already a fully-featured random-access iterator. The language gave you one for free the moment you allocated an array. Your job is not to build an iterator; it is to hand out the two you already have.

Is that really how std::vector does it?

Close enough that the difference is not about capability. Most real implementations wrap the pointer in a thin class so that (a) Vector<int>::iterator and int* are distinct types, which makes overloading and error messages behave, and (b) debug builds can bounds-check. libstdc++ calls the wrapper __normal_iterator. It is the same pointer inside, with the same arithmetic. Starting from the raw pointer is the honest version of the idea, and upgrading to a wrapper later changes no caller.

Knowledge 2Why end() points past the last element

Every C++ range is half-open: [begin, end). begin() points at element 0; end() points at the slot after the last element, which holds nothing you may read.

Three things fall out of that choice, and they are why every container in the standard library uses it:

  • The empty range is not a special case. When m_size is 0, begin() and end() are the same address, so while (it != end) runs zero times with no extra test. A closed range [first, last] would need “unless it is empty” written into every loop.
  • The count is the subtraction. end() - begin() is exactly the number of elements. No off-by-one anywhere.
  • Forming the address is legal; reading it is not. The standard specifically permits computing a one-past-the-end pointer of an array. Dereferencing it is undefined behaviour. So end() is a legal value that exists only to be compared against.

Build 1Six lines, plus the const one you owe from Monday

include/containers/vector.hpp — in the public section, next to operator[]

        T &operator[](std::size_t index) { return m_data[index]; }
        const T &operator[](std::size_t index) const { return m_data[index]; }

        using iterator = T *;
        using const_iterator = const T *;

        iterator begin() { return m_data; }
        iterator end()   { return m_data + m_size; }

        const_iterator begin() const { return m_data; }
        const_iterator end()   const { return m_data + m_size; }

Note m_size, not m_capacity. The buffer may have eight slots while you have stored three values; the other five were default-constructed by new T[] and mean nothing. An iterator range must cover the elements you stored, never the slots you own.

The const half, which is the part actually worth understanding

You have four functions above where two would do, and the duplication is not laziness. Try the old header with a const vector and the compiler tells you precisely what is wrong:

$ clang++ -std=c++20 -Iinclude -fsyntax-only probe.cpp
error: no viable overloaded operator[] for type 'const containers::Vector<int>'
    3 | void probe(const containers::Vector<int> &v) { (void)v[0]; }
      |                                                       ~^~
include/containers/vector.hpp:29:12: note: candidate function not viable: 'this' argument
      has type 'const containers::Vector<int>', but method is not marked const

Read the note carefully, because it explains the whole mechanism. Every member function has a hidden first parameter, this. In T &operator[](std::size_t) that parameter is Vector*. Writing const after the parameter list changes it to const Vector* — that trailing const applies to this, which is why it appears in such an odd position.

A const Vector& will not bind to a function whose this is non-const, because that would silently throw away a promise. So a const vector cannot call any of your non-const members — not operator[], and until now not size() either, had you not marked it. It is a hard wall, and the only way through is to supply the const overload.

The return types differ for the same reason. const T& hands back a reference the caller cannot assign through, so cv[0] = 9 fails to compile rather than quietly mutating something the caller promised not to touch.

Why this matters more than it looks

Almost every function you will write from P2 onward takes its arguments as const Something& — that is the default way to pass a non-trivial object in C++, and Core Guideline F.16 says so outright. A container that cannot be read through a const reference cannot be passed to any of them. Missing const overloads do not fail locally; they fail at every future call site.

VerifyAlgorithms you never wrote, running on a container you did

Add this to tests/main.cpp, with #include <algorithm> and #include <numeric> at the top:

    containers::Vector<int> v;
    for (int x : {50, 20, 40, 10, 30}) v.push_back(x);

    std::sort(v.begin(), v.end());
    for (int x : v) std::cout << x << " ";          // range-for, see below
    std::cout << "\n";

    auto it = std::find(v.begin(), v.end(), 40);
    std::cout << "found at index " << (it - v.begin()) << "\n";
    std::cout << "sum " << std::accumulate(v.begin(), v.end(), 0) << "\n";

    const containers::Vector<int> &cv = v;           // the const path
    std::cout << "cv[0] " << cv[0]
              << "  count " << std::count(cv.begin(), cv.end(), 30) << "\n";

Measured, -Wall -Wextra -Wpedantic -Werror, Apple clang 17:

10 20 30 40 50
found at index 3
sum 150
max 50
cv[0] 10  count 1

Sit with that for a second. std::sort is an introsort — quicksort that falls back to heapsort at depth, then insertion sort at the tail — written years ago by people who have never seen your header. It just sorted your hand-rolled buffer. You did not implement an interface, register a type, or inherit from anything. You supplied two pointers, and every algorithm in <algorithm> became available at once. That is what people mean when they say C++ generic programming is structural rather than nominal.

The range-based for came free too

You did not add anything to make for (int x : v) work. It compiles because the language defines that loop as a rewrite:

for (int x : v) { ... }

// the compiler expands this to roughly:
auto && range = v;
auto first = range.begin();
auto last  = range.end();
for (; first != last; ++first) { int x = *first; ... }

Members named exactly begin and end are the entire contract. Name them start and finish and the loop stops compiling. This is a pattern you will meet repeatedly in C++: a language feature defined as a rewrite into ordinary calls, which your own type can satisfy.

Knowledge 3The bug you just made possible

Handing out pointers into your buffer hands out something that can outlive the buffer. Here is the whole bug in seven lines:

inv.cpp

    containers::Vector<int> v;
    v.push_back(1);
    v.push_back(2);                 // size 2, capacity 2 - full

    int *p = v.begin();             // points into the current buffer
    std::cout << "before: " << *p << "\n";

    v.push_back(3);                 // grow() reallocates; p now dangles
    std::cout << "after:  " << *p << "\n";

grow() does what Lesson 5 taught it to do: allocate a new buffer, move the elements across, delete[] the old one. p still holds the old address. It now points at freed memory. This is iterator invalidation, and it is the third of the three failures in your mission statement — not a double free, not a leak, but a live pointer into a buffer that moved out from under it.

Run it under the asan preset. Real output, trimmed to the two stacks that matter:

==40071==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000130
READ of size 4 at 0x602000000130 thread T0
    #0 0x000100cfcb60 in main inv.cpp:9

0x602000000130 is located 0 bytes inside of 8-byte region [0x602000000130,0x602000000138)
freed by thread T0 here:
    #0 ... in _ZdaPv                                  <-- operator delete[]
    #1 0x000100cfd444 in containers::Vector<int>::grow()      vector.hpp:130
    #2 0x000100cfce4c in containers::Vector<int>::push_back(int const&) vector.hpp:23
    #3 0x000100cfcae4 in main                                  inv.cpp:8

Learn to read this shape, because you will see it for the rest of the term. It is two stacks, not one, and the second is the valuable one:

  • The first stack is where you got caught — inv.cpp:9, the read through p. That is the symptom, and it is the only line a debugger would have shown you.
  • “freed by thread T0 here” is where the damage was done — line 8, one line earlier, inside a push_back that looks completely innocent. ASan remembered the free and replayed it for you. Without it you would be staring at line 9 asking why a pointer you set two lines ago is wrong.
  • Note that reading p on line 7 was fine. The pointer was valid, then an unrelated-looking operation made it invalid. Nothing about p changed.

The rule this teaches, which you should be able to say without notes: any operation that can reallocate invalidates every iterator, pointer and reference into the container. For your Vector, that is push_back. cppreference states the same rule for std::vector, and says so on the push_back page — this is not a flaw in your implementation, it is the documented behaviour of the real one. You have just reproduced it from the inside.

Before you reach for a fix

There isn't one, at this level. std::vector does not prevent this either — it documents it. The professional answer is an index instead of an iterator when you intend to mutate while traversing, plus a sanitizer build as part of your normal loop so that when it does happen you find out in one second rather than one afternoon. That is why the asan preset exists in this repo.

SkillRetrieval

  1. How does std::sort decide your type is an iterator?

    • It checks an implemented interface
    • It looks up a registered trait
    • It uses the required operations
    • It requires a common base

  2. What does end() point at?

    • One slot past the last
    • The final stored element
    • The last allocated slot
    • The buffer's final byte

  3. What does the trailing const apply to?

    • The value being returned
    • Every member being read
    • The index parameter given
    • The hidden this pointer

  4. Why did for (int x : v) compile with no extra work?

    • Vector is a standard container
    • It expands to begin and end
    • The element type is simple
    • The compiler unrolls the loop

  5. Why did push_back break a pointer taken earlier?

    • Growth frees the old buffer
    • The element was moved twice
    • Size passed the capacity check
    • The pointer was never const

Out loud, as if Prof. Roy asked in review: your Vector hands out raw T* as its iterator. Defend that, and then say what the real std::vector does differently and why.

A T* already supports every operation a random-access iterator needs — dereference, increment, comparison, arithmetic — so it satisfies the requirement with no wrapper. Real implementations wrap it in a thin class for two reasons, neither of them capability: it makes Vector<int>::iterator a distinct type from int* so overloading and diagnostics behave, and it gives a debug build somewhere to put bounds checks. The wrapper holds the same pointer and compiles to the same code, and swapping it in later changes nothing at any call site.
