Load Factor, and Why Rehash Is Not grow()

Your map has 8 buckets and always will. That is not a missing feature, it is a false advertisement: a hash map that cannot grow is not O(1), it is a fixed number of linked lists, and at 800 keys it behaves like one. Fixing it looks at first like copying Vector::grow() across. It is not, and the reason why is the one idea in this lesson.

Knowledge 1Load factor is just average chain length

One number describes how crowded the table is:

load_factor = m_size / bucket_count      // entries per bucket, on average

It is worth seeing that this is the cost of a lookup. Finding a key is: one hash, one modulo, one array index — all constant — and then a linear walk down whatever chain is in that bucket. So the average lookup is constant work plus the average chain length, and the average chain length is the load factor. Keep the load factor bounded by a constant and lookup is O(1). Let it grow with n and lookup is O(n), no matter that you called the structure a hash map.

Here is what your current header actually does. Measured, same 800 keys, one table allowed to grow and one pinned at 8 buckets:

112 versus 4. A worst-case lookup that reads 112 entries and compares 112 strings is not a different constant from one that reads 4 — it is a different complexity class, and it gets worse forever as you insert. This measurement is the justification for the whole lesson, and it belongs in the writeup.

Knowledge 2The idea: rehash is not relocation

Here is the trap. You have solved “this container ran out of room” once already, in Vector::grow(), and the shape looks identical: allocate a bigger thing, move the contents across, release the old one. So the instinct is to reuse the shape.

It does not transfer, and the reason is one sentence:

In a Vector, an element's index is a property of the element. In a hash map, it is a property of the table size.

v[3] is the fourth element before growth and the fourth element after. Its index never depended on the capacity. But a key's bucket is hash(key) % bucket_count — change bucket_count and every single index changes. Move chain 0 into the new chain 0 and you have built a table in which almost nothing can be found, because find will compute the new index and look somewhere else.

So rehashing is not a relocation, it is a rebuild: construct a whole new bucket array, then re-ask every key where it now belongs. It is more work than grow(), and it is the price the structure charges for making the index arithmetic rather than storage.

Build 1rehash, and the automatic trigger

include/containers/hash_map.hpp — public section

        static constexpr double max_load_factor = 0.75;

        double load_factor() const
        {
            return static_cast<double>(m_size) / static_cast<double>(m_buckets.size());
        }

        void rehash(std::size_t new_bucket_count)
        {
            Vector<Vector<Entry>> fresh;                 // 1. build the new table
            for (std::size_t i = 0; i < new_bucket_count; ++i)
                fresh.push_back(Vector<Entry>{});

            for (std::size_t b = 0; b < m_buckets.size(); ++b)   // 2. re-ask every key
            {
                Vector<Entry> &chain = m_buckets[b];
                for (std::size_t i = 0; i < chain.size(); ++i)
                {
                    std::size_t nb = std::hash<K>{}(chain[i].key) % new_bucket_count;
                    fresh[nb].push_back(std::move(chain[i]));     // move, not copy
                }
            }

            m_buckets = std::move(fresh);                 // 3. adopt it
        }

And the trigger, at the end of insert, after ++m_size:

            if (load_factor() > max_load_factor)
                rehash(m_buckets.size() * 2);

Three things to notice, each a callback to something you already own:

  • The static_cast<double> is not decoration. Both members are std::size_t, so m_size / m_buckets.size() is integer division: 6/8 is 0, 7/8 is 0, and your load factor is 0 until it suddenly becomes 1. The rehash would never fire. Cast one operand and the whole expression becomes floating point.
  • std::move(chain[i]) is Lesson 9's fix, in its second home. The old table is about to be destroyed, so its entries have no future — copying them is pure waste, and for a V that owns memory it is an allocation per entry per rehash. Record 0009 predicted exactly this: rehash is the same relocate-and-destroy operation as grow(), and the same mistake was available here.
  • m_buckets = std::move(fresh) is your move assignment from Lesson 8. One line, and the old bucket array is released by the operator you wrote three blocks ago. If you had not written it, this would deep-copy 2048 chains and then destroy the original. The Rule of Five is paying rent here.
Why 0.75, and why doubling

0.75 is the conventional threshold (Java's HashMap uses it too) and the reasoning is a trade you can state: a lower threshold means shorter chains but more empty buckets and more frequent rehashes; a higher one means less memory and longer chains. Below about 1.0 the average chain is short enough that the constant factors dominate, so 0.75 buys most of the benefit.

Doubling is the same amortization argument as Vector, and you should be able to give it: rehashing n entries costs O(n), but doubling means it happens at sizes 8, 16, 32, 64 …, so the total rehash work to reach n entries is n + n/2 + n/4 + … < 2n. Spread over n inserts, that is a constant per insert. Amortized O(1) means exactly this: a few inserts are expensive, the average is not.

VerifyWatch it grow, then break it on purpose

Insert 40 keys and print the table state at every rehash. Measured:

  n   buckets  load   longest
  1       8    0.12      1
  2       8    0.25      1
  3       8    0.38      2
  6       8    0.75      3
  7      16    0.44      2   <- rehash
 13      32    0.41      3   <- rehash
 25      64    0.39      3   <- rehash
 40      64    0.62      3
found after rehashing: 40 / 40

Read the load column: it climbs to the threshold, the table doubles, and it drops back to roughly half. That sawtooth is the structure working. The longest chain never exceeds 3 while the entry count grows sixfold — that is the O(1) claim becoming true.

The last line is the one that matters. Look up all 40 keys after four rehashes. A rehash that moved chains wholesale instead of re-hashing would still print a plausible bucket count and a plausible load factor, and would silently fail to find most of the keys. Nothing else in the transcript catches that.

Then do it with a V that owns memory

Record 0009's rule, applied: an int-valued map cannot see the difference between a rehash that moves and one that copies, and cannot catch a rehash that double-frees. So test with HashMap<std::string, Vector<int>> from the first run, not as a follow-up. Under the asan preset, 40 keys each holding a 5-element Vector, through four rehashes:

size 40  buckets 64
intact after rehashing: 40 / 40
exit 0, no sanitizer report

Every value still owns its own buffer, every buffer is still exactly right, nothing was freed twice. That single test exercises your Vector's move constructor, move assignment, destructor and deep copy all at once, from inside a different container.

Knowledge 3Two things this breaks, and one the standard library does better

Rehashing invalidates everything. Same rule as Lesson 10, same underlying cause: the buffers moved. Any pointer, reference or iterator into the map is dangling after an insert that triggers a rehash. Note this now, because Lesson 13 gives you an iterator to invalidate.

Your bucket count is a power of two, and that is a real weakness. Doubling from 8 gives 16, 32, 64 … and % 2^k keeps only the low k bits of the hash. Any structure in those low bits survives into the bucket index. Combine that with std::hash<int> being the identity function on this machine (Lesson 11) and you get a reproducible disaster:

key 0  -> bucket 0        key 24 -> bucket 0
key 8  -> bucket 0        key 32 -> bucket 0
key 16 -> bucket 0

Every multiple of 8 in bucket 0. A map with integer keys that happen to be aligned — addresses, IDs, offsets, timestamps in even units — degenerates into one long chain, and no amount of rehashing helps, because doubling the table preserves the property.

Here is what std::unordered_map does instead, measured on this machine by inserting into one and printing bucket_count() at every change:

n=1   buckets=2        n=24  buckets=47
n=3   buckets=5        n=48  buckets=97
n=6   buckets=11       n=98  buckets=197
n=12  buckets=23       n=198 buckets=397
max_load_factor 1

Primes, not powers of two. 2, 5, 11, 23, 47, 97, 197, 397 — still roughly doubling, so the amortization argument is unchanged, but % prime mixes the whole hash into the index rather than keeping the low bits, which defends against exactly the failure above. libc++ pays a real cost for this — integer division by a runtime value is far slower than the single bitmask a power-of-two table compiles to — and takes it anyway, because a predictable pathological case is worse than a slower modulo.

Note also max_load_factor 1, not 0.75: the standard library tolerates longer chains than you do, because its buckets are better distributed.

Do not change your implementation. Power-of-two doubling is fine for the string keys in your tests, the fix is a prime table or a hash mixing step, and both are more interesting as a finding in the writeup than as an untested change five days before the deliverable. This is a measured, named, explained limitation of your container — which is precisely what the deliverable asks for: “an honest account of where the standard library wins and why.”

SkillRetrieval

  1. Why can rehash not just move chains across?

    • The chains may be too long
    • Moving would copy each value
    • Every index is recomputed
    • The old table is still live

  2. What does the load factor measure?

    • The average chain length
    • The fraction of used slots
    • The collisions per insert
    • The bytes wasted per key

  3. What breaks without the static_cast<double>?

    • The value overflows at scale
    • Rehash fires on every insert
    • The comparison never compiles
    • The table never grows at all

  4. Why is insertion amortized O(1) despite rehashing?

    • Rehashing runs in the background
    • Doubling makes the total linear
    • Most inserts skip the chain
    • The load factor stays below one

  5. Why does libc++ size its table in primes?

    • Powers of two keep low bits
    • Primes make division faster
    • It halves the memory used
    • Doubling would break amortizing

Out loud: you tested the rehash with HashMap<std::string, Vector<int>> rather than HashMap<std::string, int>. Say why that was the deliberate choice and what the int version could not have told you.

Because rehash is a relocate-and-destroy: it moves every entry into a new table and then destroys the old one. With V = int, moving and copying compile to the same instructions and there is no owned buffer to double-free, so a rehash that copies instead of moves, or one that leaves the old entries owning memory they have handed away, produces identical passing output. With V = Vector<int> each value owns a heap buffer, so the same test exercises the move constructor, move assignment and destructor at once, and ASan sees any double free. It is record 0009's rule: a container is only as tested as its most demanding element type.

Read this one first. cppreference's unordered_map load-factor and rehash pages are short and are the specification your container is imitating — read what the standard promises about invalidation, since that is the part you must match in the writeup.
