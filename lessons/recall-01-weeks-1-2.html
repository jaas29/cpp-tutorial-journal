Lesson 1 · Four Programs, Not One

The build pipeline

Say it out loud Name the four programs that run when you type clang++ main.cpp, in order, and what each one produces.

Preprocessor → a translation unit (one .cpp with every #include pasted in, recursively). Compiler → assembly. Assembler → a .o object file plus a symbol table. Linker → the executable. Stop after each with -E, -S, -c, and nothing.

What does the compiler see, and what does the linker see? Why does the difference matter?

The compiler sees exactly one translation unit at a time and knows all the types in it. The linker sees every .o at once but only names, no types. That asymmetry is why a signature mismatch is invisible to the compiler and only shows up at link time, as a missing name.

Lesson 3 · Record 0003 · Your own Log bug

Declarations, definitions, and the source list

Say it out loud You put Log.cpp in src/ and the build failed. Why did adding the file not add it to the build?

Nothing scans directories. add_executable is the sole statement of which translation units exist. Log.cpp was never compiled, produced no .o, and therefore supplied no symbol. Meanwhile main.cpp compiled fine, because the declaration void Log(const char*); was all the compiler ever needed.

Why does that error message name main.cpp.o — the file that is correct — and never mention Log.cpp?

Because the build system does not know Log.cpp exists. The linker can only report the hole it found and which object file wanted it filled. It cannot name a file nobody ever told it about. This is the general shape: the error names the caller, never the missing thing.

How did you actually prove it, rather than guessing?

Read the symbol tables. nm -u build/…/main.cpp.o | c++filt showed the undefined hole (Log(char const*)), and hand-compiling Log.cpp showed the matching T __Z3LogPKc that was never reaching the link.

  1. Log.cpp is in add_executable, but the header declares void Log(const char*) and the .cpp defines void Log(std::string). What happens?

    • Compiler error: mismatched declaration
    • Links fails: undefined symbol, same as before
    • Builds and runs; the string converts
    • Linker warning, but it links

Lessons 2 & 4 · Record 0004

What CMake is for

Say it out loud — likely question You could build P1 with four clang++ commands. So what does CMake actually buy you? Give the load-bearing reason, not the convenience one.

The dependency graph. A shell script cannot know which .cpp included which header, so it must rebuild everything or risk linking stale objects. CMake records that graph — you saw it in build/CMakeFiles/app.dir/compiler_depend.make. Editing vecutil.cpp rebuilt one file; editing log.hpp rebuilt all three. The other two reasons are flag drift and needing two configurations, but the graph is the one you cannot reproduce by hand.

Complete the sentence: “CMake is a …, not a …” — and say why the workflow therefore has two commands.

A generator, not a build system. It writes Makefiles into build/; make runs them. Hence cmake --preset dev (configure, generate) and then cmake --build --preset dev (actually compile), and hence why you only re-run the first one when CMakeLists.txt changes.

Why does every CMake command start with target_?

Because properties belong to targets, not to the whole directory. target_include_directories(containers INTERFACE …) means anything that links containers inherits that include path automatically. The old directory-wide commands leak settings into things that should not have them.

Record 0002 · Your own repo

Why P1's build is shaped the way it is

These four are decisions you made and will be asked to defend. They are the most likely opening questions of the meeting.

Say it out loud — likely question Why add_library(containers INTERFACE) rather than a normal compiled library?

Because vector and unordered_map are class templates. A template has no code to compile until it is instantiated, so it must live entirely in headers — there is nothing to put in a .a. INTERFACE is CMake's name for exactly that: a named bundle of include paths and flags with no compilation of its own.

Why two separate build directories rather than one directory with two flag sets?

CMake caches CMAKE_CXX_COMPILER per build directory, and object files from Apple clang and Homebrew clang must never be linked together. Separate directories make mixing structurally impossible rather than merely unlikely.

Why -Werror from day one? It is not the comfortable choice.

A warning you can ignore is a warning you will ignore, and in C++ the warnings are load-bearing — sign conversion, uninitialised reads, shadowing. Making them fatal means the class of bug is caught at build time rather than by a sanitizer at runtime, or not at all. It is on in P1 and deliberately off in the mystl sandbox, where the point is to see what the compiler complains about.

Why is -isysroot hardcoded in the asan preset, and what is the cost of that?

Homebrew clang cannot find the system headers without it — verified, it fails inside <iostream> with no such sysroot directory. JSON cannot run commands, so $(xcrun --show-sdk-path) cannot be evaluated there and the path has to be literal. Cost: it needs regenerating after an Xcode update.

Record 0001 · The finding worth leading with

Why this machine needs two compilers

Say it out loud — lead with this Walk through the Apple-clang ASan bug: symptom, cause, fix.

Symptom: any binary built with /usr/bin/clang++ -fsanitize=address compiles and links fine, then hangs on startup with no output at all. Not a crash — it never begins. Cause: macOS 26's dyld allocates inside the routine ASan calls to enumerate memory mappings; that allocation hits ASan's own intercepted malloc, which re-enters the initialiser and spins forever on a lock it already holds. Found by sampling the stuck process. Fix: Homebrew LLVM clang 22 has a runtime without the bug, so the asan preset points at it explicitly. UBSan is unaffected.

And why -gdwarf-4?

Homebrew's clang emits DWARF 5 by default and Apple's linker cannot read it. Without the flag, sanitizer reports come back as raw addresses instead of file and line numbers — the tool still works, but the output is useless.

Lesson 5 · This week's C++

Pointers, the heap, and Vector

Say it out loud Why can a stack variable not hold a buffer whose size you only learn at runtime?

Stack layout is decided at compile time — the compiler emits one fixed frame size, baked into the executable before the program runs. A runtime-sized buffer has no compile-time size, so it must come from the heap. That is the only reason new is in this file.

What are the three members of your Vector, and what is the invariant that must hold after every operation?

m_data (address of the heap buffer, or nullptr), m_size (how many the caller stored), m_capacity (how many slots you own). Invariant: m_size <= m_capacity. Every bug in the file is a violation of that one line.

Say it out loud — likely question Name the four steps of grow() in order, and say what breaks if you swap two of them.

1. Allocate a bigger buffer. 2. Copy the old values across. 3. delete[] the old buffer. 4. Adopt the new one (m_data and m_capacity). Swap 2 and 3 and you copy out of memory you have already returned to the allocator — it compiles, and it frequently still prints the right answer, which is what makes it hard to find.

Why does the copy loop run to m_size and not m_capacity?

Slots between size and capacity have never been written. Copying them would read uninitialised memory for no benefit.

Say it out loud — likely question Why double the capacity instead of growing by one? Give the complexity argument.

Copying dominates. Growing by one reallocates on every push, so n pushes cost 1+2+…+n copies — n²/2, quadratic. Doubling makes reallocation geometric: n + n/2 + n/4 + … sums to under 2n. So an individual push is occasionally expensive but the average over any run is constant. The phrase is amortised constant time.

  1. Pushing 5 values into an empty Vector, how many times does grow() run?

    • 5 — once per push
    • 3
    • 4
    • 2

  2. Why does grow() special-case m_capacity == 0?

    • To avoid calling new with a negative size
    • Because doubling zero is still zero
    • Because delete[] on nullptr crashes
    • To keep the first allocation cheap

  3. You wrote m_data[m_size++] = value; followed by ++m_size;. What is the worst consequence?

    • size() reports double the real count
    • Every other slot is left uninitialised
    • Extra memory is wasted
    • grow() never runs again, so writes go past the end

Records 0005 & 0006 · Found while verifying, 25–26 Aug

The leak, and the blind spot

Your Vector leaks. Precisely which buffer, and why not the others?

Only the final one. grow() calls delete[] on each old buffer as it replaces it, so the intermediates are fine. But nothing frees the last one: when v goes out of scope its three members vanish, including m_data — the only record of where that buffer lived. Still allocated, now unreachable.

Say it out loud — likely question Is P1 clean under the sanitizers?

Clean under both presets — but that claim is weaker than it sounds, because neither preset can detect a leak. The asan preset cannot because LeakSanitizer is unsupported on Darwin. The dev preset cannot because -fsanitize=undefined makes Apple's leaks report zero — verified by holding the source constant and varying only that flag. Leak checking needs a third, plain, uninstrumented build. A leak in P1 would currently pass every configuration I have defined.

Why does the leak report point at grow() rather than at the destructor you did not write?

Leak tools always name the allocation site. The delete[] you forgot has no location — the forgetting did not happen anywhere. Read the stack bottom-up and it is the call chain: main called push_back, which called grow, which called new[].

    • The asan preset
    • leaks
    • None; it is silent corruption

  2. A missing delete[] — which build catches it?

    • The dev preset
    • The asan preset
    • A plain uninstrumented build, run under leaks
    • Either preset, run under leaks

Looking forward · What she will ask next

The two questions you cannot answer yet

Knowing where the edge of your knowledge is counts for more than pretending it is further out than it is. Both of these are fine to answer with “that is next.”

You add ~Vector() { delete[] m_data; }. What new bug have you just created?

A double free. Copying the vector now gives two objects holding the same pointer, and both destructors will free it. That is why the destructor comes bundled with the copy constructor and copy assignment as a set — the Rule of Three. Saying this before she does is worth a lot.

What is still missing between what you have and the P1 deliverable?

Templates (Vector<T> rather than hardcoded int), copy and move semantics, STL-compatible iterators, and the whole of unordered_map. The Sep 2 checkpoint is close, and the honest framing is that the remaining lessons are the checkpoint rather than preparation for it.

The four steps of grow() and what breaks if you reorder them; the amortised constant time argument for doubling; and the leak blind spot in both presets. The first two are the code review. The third is the thing you found that she does not already know.
