Measuring It, and the Preset That Lies

Every performance claim you have made in this project so far has been an argument. Amortized O(1), the cost of chaining, where the standard library wins — all reasoned, none measured. This is the lesson that turns them into numbers, and the first number you get says your hand-written vector is 2.4× faster than std::vector. It is not. Finding out why that number is a lie is more valuable than the benchmark itself.

Knowledge 1How to time something without fooling yourself

Four rules, and each one exists because skipping it produces a confidently wrong number.

1. Use steady_clock

using clk = std::chrono::steady_clock;

auto a = clk::now();
work();
auto b = clk::now();
double milliseconds = std::chrono::duration<double, std::milli>(b - a).count();

<chrono> gives you three clocks and only one is for this. system_clock is wall-clock time, which NTP can adjust mid-measurement — it can run backwards. steady_clock is guaranteed to only move forward at a constant rate, which is exactly and only what a duration needs.

The duration<double, std::milli> cast is deliberate too: subtracting two time points gives a duration in the clock's native tick, which is nanoseconds here. Converting to double milliseconds keeps fractions instead of truncating them to integers.

2. Take a median of several runs, not one run

The first run pays for cold caches and page faults, and any run can be interrupted by the scheduler. One measurement measures your machine's mood. Five runs and take the middle one: the median discards a single outlier in either direction, where a mean would absorb it.

3. Stop the optimizer deleting the work

volatile std::size_t sink = 0;
// ... at the end of each timed block:
sink += v.size();

At -O2 the compiler is entitled to delete any computation whose result nobody observes. Build a vector, never read it, and a good optimizer removes the entire loop — and you measure 0.00 ms and believe it. Writing into a volatile forbids that: the compiler must assume the variable can be observed from outside the program, so the work that feeds it has to happen. This is the standard trick and it is worth recognising in other people's benchmarks.

4. Benchmark the build people will actually run

Which is the next section, because it is the one that would have caught you out.

Knowledge 2Your two presets are both wrong for this

Look at what p1-containers can currently build:

PresetFlagsOptimization
dev-g -fno-omit-frame-pointer -fsanitize=undefinednone

Neither passes -O anything, so both are unoptimized, and one is also carrying sanitizer instrumentation on every memory access. That has been exactly right for four weeks — you have been hunting correctness bugs, and unoptimized builds give honest line numbers. It is completely wrong for measuring speed.

Here is the same benchmark, same machine, same minute, under the dev preset and then at -O2:

200,000 operationsdev preset-O2 -DNDEBUG
vector push_back0.41× — mine is 2.4× faster1.09× — mine is 9% slower
hashmap insert2.38× slower5.36× slower
hashmap lookup (hits)0.85×0.86×

The first row is the whole point. Under dev, the measurement says you beat the standard library by more than a factor of two. That result is not noise and it is not a mistake in the timing code — it is a real property of that build, and it is meaningless. std::vector is an enormous stack of small inlinable abstractions: iterators wrapping pointers, allocator indirection, __builtin calls. At -O0 every one of those layers is a real function call that really executes. Your Vector is three members and a loop, so it has almost nothing to inline away. You did not measure a faster container. You measured a shorter abstraction tower against an optimizer that was switched off.

And the deception runs in both directions: the same dev preset made your hash map look 2.38× slower when the truth is 5.36×. It flattered you where you were losing and flattered you where you were winning. An unoptimized benchmark is not a pessimistic benchmark, it is an unrelated one.

Add a third preset

You need a release preset in CMakePresets.json, and it is worth having beyond this week — P2 is the performance project and every number in it will need this.

{
  "name": "release",
  "displayName": "Optimized build (Apple clang, -O2) - for benchmarking only",
  "binaryDir": "${sourceDir}/build/release",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Release",
    "CMAKE_CXX_COMPILER": "/usr/bin/clang++"
  }
}

CMAKE_BUILD_TYPE: Release supplies -O3 -DNDEBUG on its own — you do not write the flags. And note what is absent: no sanitizers. Never benchmark a sanitizer build and never ship a correctness claim from a release build. They answer different questions, which is why they are different presets.

VerifyThe real numbers

Apple clang 17, -O2 -DNDEBUG, median of 5, 200,000 operations, macOS 26.5 arm64. Ratios above 1.00 mean the standard library wins:

OperationMine (ms)std (ms)Ratio
vector push_back, 200k int0.210.191.09×
hashmap insert, 200k string keys59.3511.085.36×
hashmap lookup, 200k hits3.093.600.86×
hashmap lookup, 200k misses5.588.830.63×

Three results, and the two surprising ones are the interesting ones.

The vector is a real result. Within 9% of std::vector for int push_back. That is not a moral victory — it is what should happen, because at -O2 both compile down to roughly the same bounds check, store and increment. It says your growth strategy is right and you are not doing anything stupid per element.

Your lookup beats the standard library, and you can explain why. 0.86× on hits, 0.63× on misses, and both come from decisions in Lesson 12:

  • Your max_load_factor is 0.75; libc++'s default is 1.0. Shorter chains, fewer comparisons per lookup.
  • Your bucket count is a power of two, so % bucket_count compiles to a single bitmask instruction. libc++ uses prime bucket counts, so its modulo is a genuine integer division by a runtime value — one of the slowest integer operations on the machine.

Notice what that means. The power-of-two bucket count that Lesson 12 called a weakness is the same decision that is winning here. Both statements are true: it is faster on these keys, and it has a pathological case libc++ paid for this speed to avoid. That is what an engineering trade-off actually looks like when you measure it rather than argue it, and it is the single best thing you have to say in review.

Knowledge 3Finding the cause of the 5.36×

A benchmark that reports a number is half a benchmark. The deliverable asks for “an honest account of where the standard library wins and why,” so the 5.36× needs a cause, not a shrug. You find it the same way you would find any performance problem: form a hypothesis and measure it away.

Hypothesis 1: it is the rehashing. Test it by giving the map all its buckets up front, so no rehash ever fires, and re-timing:

mine, growing from 8       :  84.20 ms
mine, buckets preallocated :  33.09 ms      <- rehashing was 61% of the time
std, reserved              :   8.63 ms

Confirmed, and only partly. Rehashing is 61% of insert cost — but with rehashing entirely removed you are still 3.8× slower than the standard library. Something else is going on per-insert.

Hypothesis 2: you are copying the key more than once. Timing cannot tell you this, so stop timing and start counting. Make a key type that records every operation performed on it:

struct Counted {
    std::string s;
    static inline int copies = 0, moves = 0, defaults = 0;
    Counted() { ++defaults; }
    Counted(const Counted &o) : s(o.s) { ++copies; }
    Counted(Counted &&o) noexcept : s(std::move(o.s)) { ++moves; }
    // ... and the two assignment operators, likewise
};

100 inserts into each map. Measured:

100 insertskey copieskey movesdefault-constructions
Mine39187390
std::unordered_map1001000

There is the answer, and it is much more specific than “the standard library is optimized.” Two distinct causes, both traceable to one line of your code:

  1. ~4 copies per insert instead of 1. Entry{key, value} copies the key into a temporary Entry; then push_back(const T&) copies that Entry again into the slot. Two copies before you even count the ones rehashing adds. The standard library does one, because insert takes the pair by value and moves it into place.
  2. 390 default-constructions that should not exist at all. You never asked for those. They come from new T[n], which default-constructs every slot in every buffer — including the empty ones, and again in every fresh buffer every time a chain or the bucket array grows. std::unordered_map does exactly zero, because it never allocates an object it has not been asked to store.

And both trace to the same root: new T[n] allocates and constructs, where the standard library allocates raw bytes and constructs in place. You wrote that limitation down in Lesson 9, met it again in Lesson 13 when pop_back could not destroy anything, and here it is a third time with a price tag attached. Three independent symptoms, one cause, now measured.

Do not fix it this week. The fix is raw storage plus placement new plus explicit destructor calls, it touches every member of both containers, and it is five days before the deliverable. Write it up instead. “Here is my 5.36× gap, here is the measurement isolating it to 61% rehash and ~4× key copies, here is the single root cause, here is the named technique that fixes it, and here is why I did not do it in week four” is a stronger thing to bring to a code review than a faster container would be.

SkillRetrieval

  1. Why steady_clock rather than system_clock?

    • It has a finer resolution
    • It excludes any idle time
    • It cannot be adjusted backward
    • It reads the counter directly

  2. Why did the dev preset say your vector wins?

    • Nothing was inlined away
    • Sanitizers slowed the heap
    • The loop was deleted entirely
    • Debug info bloated the code

  3. What is the volatile sink for?

    • Flushing the cache between runs
    • Keeping the timing thread awake
    • Preventing integer overflow
    • Stopping the work being deleted

  4. Why is your lookup faster than libc++'s?

    • Chaining beats their probing
    • Shorter chains, cheaper modulo
    • Your hash function is simpler
    • Fewer indirections per bucket

  5. Where did 390 unrequested constructions come from?

    • new T[n] fills every slot
    • Each rehash copies the keys
    • Entry has a default member
    • The chains were copied twice

Out loud, as if Prof. Roy asked: your hash map inserts 5× slower than the standard library's. Account for it — and do not say “theirs is more optimized.”

Two causes, both measured. Preallocating the buckets so no rehash fires cuts insert time from 84 ms to 33 ms, so rehashing is 61% of it — my rehash rebuilds the whole table because every bucket index is recomputed. The rest is per-insert: instrumenting the key type shows 391 key copies and 390 default-constructions per 100 inserts, against 100 and 0. The copies are because I build an Entry temporary and then push_back copies it again, where insert takes its pair by value and moves it once. The default constructions are because new T[n] allocates and constructs every slot, including empty buckets and every fresh buffer, where the standard library allocates raw bytes and constructs in place with placement new. Both trace to the same root cause, it is the same one that stops my pop_back destroying anything, and the fix is raw storage plus placement new — which I deliberately deferred past the deliverable because it touches every member of both containers.
