Iterating a Bucketed Structure, and the Five Typedefs

In Lesson 10 the iterator was a pointer and the lesson was that you already had one. Here you have to build the thing, because there is no single pointer that walks a table of chains. Then something instructive happens: the range-based for works immediately, and std::count_if does not compile at all. The gap between those two facts is std::iterator_traits, and it is the last piece of the checkpoint sentence “iterators that work with STL algorithms.”

Knowledge 1A position in two dimensions, not one

Walking a Vector is walking a line. Walking a hash map is walking a ragged table:

So the iterator has to hold two numbers, not one: which bucket, and how far down that bucket's chain. Plus a pointer to the table, since it has to be able to look at the other buckets to find where to go next.

That gives operator++ a job it did not have in Lesson 10. Stepping forward inside a chain is easy. Stepping off the end of a chain means walking forward through buckets — possibly several empty ones in a row — until you find one with something in it, or you run out of table. Get that wrong in either direction and you either skip entries or dereference an empty bucket.

The invariant that makes it manageable

Do not try to write that logic inside operator++. Write down a rule the iterator obeys at all times, put it in one function, and call that function after every move:

An iterator is always either sitting on a real entry, or sitting exactly on the end position. Never in between.

            void settle()
            {
                while (m_bucket < m_buckets->size() &&
                       m_index >= (*m_buckets)[m_bucket].size())
                {
                    ++m_bucket;
                    m_index = 0;
                }
            }

Read the condition as one sentence: while there is still table left, and I have run past the end of the chain I am in, move to the start of the next bucket. When it stops, either m_bucket has reached the bucket count (that is the end position) or m_index is a valid slot in a non-empty chain. Exactly the two legal states, no others.

The payoff is that three separate problems become one. Call settle() from the constructor and from operator++, and all of these fall out with no extra code:

  • Leading empty buckets. begin() is constructed at bucket 0, slot 0 even if bucket 0 is empty; settle() walks it forward to the first real entry.
  • Runs of empty buckets mid-table. The while is a loop, not an if. Ten empty buckets in a row cost ten iterations and no special case.
  • The empty map. Every bucket is empty, so settle() runs m_bucket all the way to the bucket count — which is precisely the end position. begin() == end() comes out true without a single line written to make it true.

Build 1The iterator

include/containers/hash_map.hpp — nested inside HashMap, public section

        class iterator
        {
            Vector<Vector<Entry>> *m_buckets = nullptr;
            std::size_t m_bucket = 0;   // which bucket
            std::size_t m_index = 0;    // how far down its chain

            void settle() { /* as above */ }

        public:
            iterator(Vector<Vector<Entry>> *buckets, std::size_t bucket, std::size_t index)
                : m_buckets(buckets), m_bucket(bucket), m_index(index)
            {
                settle();               // enforce the invariant on construction
            }

            Entry &operator*()  const { return (*m_buckets)[m_bucket][m_index]; }
            Entry *operator->() const { return &(*m_buckets)[m_bucket][m_index]; }

            iterator &operator++()
            {
                ++m_index;
                settle();
                return *this;
            }

            bool operator==(const iterator &other) const
            {
                return m_bucket == other.m_bucket && m_index == other.m_index;
            }
            bool operator!=(const iterator &other) const { return !(*this == other); }
        };

        iterator begin() { return iterator(&m_buckets, 0, 0); }
        iterator end()   { return iterator(&m_buckets, m_buckets.size(), 0); }

end() is constructed at (bucket_count, 0). Look at settle()'s condition and confirm for yourself that it leaves that position untouched: m_bucket < size() is already false, so the loop body never runs. The end position is a legal value that no amount of settling will move, which is what makes it a reliable stopping point — the same property m_data + m_size had in Lesson 10.

operator-> is new. It exists so that it->key works as shorthand for (*it).key. The rule is unusual and worth knowing: the compiler applies operator-> repeatedly until it reaches a real pointer, then does one final built-in ->. So returning Entry* is exactly right.

Build 2erase, in constant time

        bool erase(const K &key)
        {
            Vector<Entry> &chain = m_buckets[bucket_for(key)];
            for (std::size_t i = 0; i < chain.size(); ++i)
                if (chain[i].key == key)
                {
                    chain[i] = std::move(chain[chain.size() - 1]);  // pull the last one back
                    chain.pop_back();                               // drop the tail
                    --m_size;
                    return true;
                }
            return false;
        }

You need one three-line addition to Vector for this:

        void pop_back() { --m_size; }

The obvious way to remove element i is to shift every later element down one, which is O(chain length). The trick here is that you do not have to preserve order. The container is called unordered; nothing promises the chain is in any particular sequence. So move the last element into the hole and shorten by one: constant time, one move, no shifting. Remember this shape — swap-with-last-and-pop is the standard removal for any unordered sequence, and you will use it again in P3 for move lists.

Two honest limitations of that pop_back

It does not destroy anything. Because your buffer came from new T[], every slot holds a live, fully constructed object; m_size only records how many the caller cares about. So pop_back makes an element unreachable but leaves it alive, holding whatever it owns, until the whole buffer is deleted. For a V that owns a megabyte, an erased entry keeps that megabyte until the map is destroyed. This is the same new T[] consequence you recorded in Lesson 9, showing up in a third place. The fix is still the same one, still deferred: raw storage plus placement new and explicit destructor calls.

It does not check for empty. pop_back() on an empty Vector wraps m_size from 0 to a huge number, because std::size_t is unsigned. Your erase never calls it on an empty chain, so it is currently unreachable — but note it, because it is exactly the kind of precondition that is fine until someone else calls the function.

VerifyOrder, mutation, and the empty case

Ten keys inserted as key0…key9, then iterated. Measured under the asan preset:

range-for over the map:
  key4=4 key1=1 key7=7 key2=2 key5=5 key8=8 key3=3 key6=6 key9=9 key0=0
  visited 10 entries, values sum to 45

erase key3: 1  again: 0
size now 9   find key3: not found
iteration now visits 9

empty map: begin == end -> 1
empty map iterations: 0

after mutation key7 = 700
exit 0, no sanitizer report

Four things that transcript proves, and it is worth knowing which line proves which:

  • The scrambled order is the headline. You inserted in order and got them back in none. This is not a defect — it is why the standard container is named unordered_map. Iteration follows bucket order, and bucket order is hash order, which has no relationship to insertion order or to sorting. If you ever need order, you need std::map, which is a tree, not a table.
  • Sum 45 over 10 entries means every entry was visited exactly once. A settle() that skipped a non-empty bucket would still print a plausible list; the sum is what catches it.
  • erase returns 1 then 0 — removing a key that is there and one that is not are different answers, and the caller can tell.
  • begin() == end() on the empty map, with zero iterations. The case most likely to be wrong, and you wrote no code for it.

The last line is for (auto &e : m) e.value *= 100;, and it works because operator* returns Entry&. That is the thing std::optional could not do: your find hands back a copy, but your iterator refers to the stored entry, so you can write through it. You have just built the more capable of the two return types the standard library offers — which is the honest reason it returns an iterator from find.

Knowledge 2Why std::count_if refuses

The range-based for works. Now try an algorithm:

std::count_if(m.begin(), m.end(), [](auto &e){ return e.value > 4; });

error: no matching function for call to 'count_if'

Your iterator does everything count_if needs at runtime — it dereferences, it increments, it compares. The refusal is not about capability. It is that <algorithm> asks questions about your iterator before it agrees to use it, and your iterator has no answers.

The questions go through std::iterator_traits<It>, which looks for five member typedefs. An algorithm needs to know what *it yields so it can name a local variable of that type; it needs a type in which to count distances; and above all it needs to know how powerful your iterator is, because std::sort must reject a forward-only iterator rather than fail mysteriously at runtime.

That last question is answered by the iterator_category tag, and the tags form a hierarchy of capability:

CategoryAddsYours?
input_iterator_tagread once, forward
forward_iterator_tagmulti-pass: read the same range twicethis one
bidirectional_iterator_tag--itno — you cannot walk back to the previous non-empty bucket
random_access_iterator_tagit + n, b - ano — that was Lesson 10's T*

This is also the answer to a question Lesson 10 raised and did not settle: why did a raw T* work with std::sort with no declarations at all? Because the standard library ships a std::iterator_traits specialization for pointers that fills in all five answers automatically. Pointers were never exempt from the requirement — someone had already answered for them. For your own class, you answer.

Build 3Five typedefs

include/containers/hash_map.hpp — top of the iterator's public section, plus #include <iterator>

            using iterator_category = std::forward_iterator_tag;
            using value_type        = Entry;
            using difference_type   = std::ptrdiff_t;
            using pointer           = Entry *;
            using reference         = Entry &;

            iterator() = default;          // forward iterators must be default-constructible

            iterator operator++(int)       // post-increment: it++
            {
                iterator before = *this;
                ++(*this);
                return before;
            }

The two extras are part of the forward-iterator contract rather than afterthoughts. A forward iterator must be default-constructible, and must support both ++it and it++ — note that post-increment is written in terms of pre-increment, returning a copy of the old position, which is why ++it is the one to prefer in your own loops.

Measured after those additions, with -Wall -Wextra -Wpedantic -Werror:

count_if value>4: 5
max: key9 = 9
distance: 10

Nine lines of declarations, and <algorithm> opened up. Nothing about the runtime behaviour changed — the same increments, the same dereferences. You did not make the iterator more capable; you made it legible. That is a distinctively C++ move, and it is the answer to the Sep 2 checkpoint sentence in full: your iterators now work with STL algorithms, on both containers, for a reason you can explain.

SkillRetrieval

  1. Why does this iterator hold two indices?

    • To detect a stale table
    • A chain, and a place in it
    • To support moving backward
    • One counts the erased slots

  2. How does the empty map get begin() == end()?

    • A size check inside begin
    • Both return a null table
    • The constructor short-circuits
    • settle runs off the table

  3. Why does erase swap with the last element?

    • Order need not be kept
    • Shifting would invalidate
    • The last one is cached
    • It avoids a reallocation

  4. Why did count_if reject the iterator?

    • It lacked a subtraction operator
    • The lambda took a reference
    • Its traits were not declared
    • The category was too weak

  5. Why did a raw T* need no typedefs in Lesson 10?

    • Algorithms special-case pointers
    • A traits specialization exists
    • Built-in types skip the check
    • Its category is deduced later

Out loud: your map's iteration order has no relationship to the order you inserted. Say why, say what that means for the container's name, and say what you would reach for if you did need order.

Iteration walks buckets in index order and each chain in storage order, and a key's bucket is its hash modulo the bucket count — a number with no relationship to insertion time or to the key's sort position. Rehashing scrambles it again. That is why the standard container is called unordered_map: unordered is a documented guarantee that you must not depend on any order, not an accident of implementation. If I needed sorted iteration I would use std::map, which is a balanced binary tree — ordered iteration and O(log n) lookup, rather than unordered iteration and O(1).
